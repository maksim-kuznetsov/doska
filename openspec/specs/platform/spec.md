# platform Specification

## Purpose

Определяет технологическую платформу доски объявлений: состав решения, доступ к данным, контракт Web API, сборку и версионирование интерфейса, работу с медиафайлами, фоновые задачи, тестирование и развёртывание. Требования этой спецификации задают технические рамки для всех остальных возможностей и не изменяют бизнес-правила.

## Requirements

### Requirement: Состав решения

Решение SHALL состоять из одностраничного приложения на Vue 3 (Composition API, TypeScript, Vite, Pinia) и серверного Web API на ASP.NET Core (целевая платформа `net10.0`, .NET 10) с базой данных PostgreSQL. Единственным источником бизнес-правил и проверок SHALL быть серверный API; интерфейс MUST NOT обращаться к базе данных напрямую.

#### Scenario: Разделение интерфейса и API

- **WHEN** интерфейс выполняет действие пользователя
- **THEN** он вызывает эндпоинт Web API, а решение о допустимости действия принимает сервер

#### Scenario: Единый источник правил

- **WHEN** одна и та же проверка нужна на разных страницах
- **THEN** она выполняется сервером, а клиентская проверка используется только как подсказка до отправки

### Requirement: Структура репозитория

Репозиторий SHALL содержать решение `Doska.sln` с проектами `src/Doska.Domain`, `src/Doska.Application`, `src/Doska.Infrastructure`, `src/Doska.Api`, `tests/Doska.Tests` и каталог `web` с приложением Vue. Границы проектов SHALL соответствовать возможностям `user-accounts`, `categories`, `locations`, `classified-ads`, `ad-moderation`, `ad-search`, `notifications`.

#### Scenario: Размещение нового сценария

- **WHEN** в проект добавляется новый сценарий использования
- **THEN** правило предметной области размещается в `Doska.Domain`, оркестрация — в `Doska.Application`, доступ к данным — в `Doska.Infrastructure`, эндпоинт — в `Doska.Api`

#### Scenario: Роли проектов решения

- **WHEN** правило предметной области, сценарий использования, доступ к данным или эндпоинт размещаются в решении
- **THEN** они попадают соответственно в `Doska.Domain` (сущности и правила), `Doska.Application` (сценарии), `Doska.Infrastructure` (EF Core, миграции, почта, файлы) или `Doska.Api` (контроллеры и конфигурация)

#### Scenario: Состав каталога web

- **WHEN** в интерфейс добавляется новый файл
- **THEN** `src/views` содержит представления (view), `src/components` — компоненты, `src/layouts` — раскладки, `src/router` — маршруты, `src/stores` — хранилища Pinia, `src/assets` — стили и изображения

#### Scenario: Зависимости проектов

- **WHEN** сборка решения выполняется с нуля
- **THEN** `Doska.Domain` не зависит от `Doska.Infrastructure` и `Doska.Api`

### Requirement: Доступ к данным через EF Core и PostgreSQL

Система SHALL обращаться к PostgreSQL через Entity Framework Core с провайдером Npgsql. Имена таблиц и столбцов SHALL формироваться соглашением `UseSnakeCaseNamingConvention`. Изменения схемы SHALL выполняться миграциями EF Core; ручная правка схемы на работающем окружении MUST NOT использоваться.

#### Scenario: Именование в базе данных

- **WHEN** сущность с составным именем свойства отображается на таблицу
- **THEN** таблица и столбцы получают имена в нижнем регистре с подчёркиваниями

#### Scenario: Изменение схемы

- **WHEN** требуется добавить или изменить столбец
- **THEN** создаётся миграция EF Core, применяемая при развёртывании

#### Scenario: Применение миграций

- **WHEN** развёртывается новая версия с неприменёнными миграциями
- **THEN** миграции применяются до запуска обработки запросов, а при ошибке релиз не переключается на новую версию

### Requirement: Контракт Web API

Все операции SHALL предоставляться как HTTP-эндпоинты с префиксом `/api` в формате JSON. Выборки SHALL принимать условия, сортировку и постраничность как query-параметры. Ошибки SHALL возвращаться в формате `ProblemDetails` с HTTP-кодом, соответствующим причине, а тела запросов и ответов MUST NOT переиспользовать сущности базы данных напрямую.

#### Scenario: Успешный вызов API

- **WHEN** клиент вызывает эндпоинт с корректными данными и правами
- **THEN** ответ содержит код 2xx и JSON-представление результата

#### Scenario: Отказ по правам

- **WHEN** клиент вызывает эндпоинт, недоступный его роли
- **THEN** ответ содержит код 403 и описание ошибки в формате `ProblemDetails`

#### Scenario: Некорректные данные

- **WHEN** клиент отправляет данные, не проходящие серверную проверку
- **THEN** ответ содержит код 400 и перечень нарушений

### Requirement: Аутентификация и авторизация

Система SHALL аутентифицировать пользователя серверной сессией в cookie с флагами `httpOnly` и `SameSite=Lax` и SHALL требовать antiforgery-токен для запросов, изменяющих состояние. Роль пользователя SHALL храниться одним значением в его записи, а проверка прав SHALL выполняться на сервере для каждого действия.

#### Scenario: Доступ к защищённому эндпоинту без сессии

- **WHEN** запрос к защищённому эндпоинту приходит без действующей сессии
- **THEN** ответ содержит код 401

#### Scenario: Изменяющий запрос без antiforgery-токена

- **WHEN** запрос, изменяющий состояние, приходит без действующего antiforgery-токена
- **THEN** сервер отклоняет запрос и не изменяет данные

#### Scenario: Скрытие прав на клиенте

- **WHEN** интерфейс скрывает недоступные элементы управления для роли пользователя
- **THEN** сервер всё равно проверяет права при вызове эндпоинта

### Requirement: Ограничение частоты запросов

Система SHALL применять ограничение частоты запросов на уровне middleware ASP.NET Core для чувствительных операций (вход, регистрация, сброс пароля, отправка объявления). Суточный лимит подачи объявлений SHALL оставаться бизнес-правилом и MUST NOT подменяться ограничением частоты запросов.

#### Scenario: Превышение частоты запросов

- **WHEN** клиент превышает разрешённую частоту обращений к чувствительному эндпоинту
- **THEN** сервер отвечает кодом 429 и не выполняет операцию

#### Scenario: Различие лимитов

- **WHEN** пользователь подаёт объявления в пределах суточного лимита, но с большой частотой
- **THEN** ограничение частоты запросов ограничивает поток запросов, а суточный лимит проверяется бизнес-правилом подачи

### Requirement: Сборка и версионирование интерфейса

Интерфейс SHALL собираться сборщиком Vite. Имена собранных файлов CSS и JS SHALL содержать хеш содержимого, а подключение файлов в разметке SHALL выполняться по манифесту сборки. В режиме разработки интерфейс SHALL обслуживаться dev-сервером Vite без предварительной сборки.

#### Scenario: Сборка для развёртывания

- **WHEN** выполняется сборка интерфейса для развёртывания
- **THEN** каталог сборки содержит файлы с хешем в имени и манифест, по которому подключаются ассеты

#### Scenario: Изменение файла стилей или скрипта

- **WHEN** содержимое файла интерфейса изменяется и сборка повторяется
- **THEN** имя собранного файла изменяется, поэтому ранее закешированная копия не используется

#### Scenario: Локальная разработка

- **WHEN** разработчик запускает dev-сервер Vite
- **THEN** интерфейс доступен с горячей заменой модулей без предварительной сборки

### Requirement: Хранение и отдача медиафайлов

Медиафайлы SHALL храниться на локальном томе сервера и SHALL отдаваться веб-сервером, а не приложением. Доступ к хранилищу SHALL выполняться через абстракцию, позволяющую заменить локальный том на S3-совместимое хранилище без изменения сценариев использования.

#### Scenario: Загрузка фотографии

- **WHEN** пользователь загружает фотографию объявления
- **THEN** файл сохраняется в хранилище, а его уменьшенная копия формируется при загрузке

#### Scenario: Отдача файла посетителю

- **WHEN** браузер запрашивает файл объявления
- **THEN** файл отдаёт веб-сервер по внутреннему перенаправлению от приложения

### Requirement: Фоновые задачи

Система SHALL выполнять периодические задачи (автоархив объявлений и письма о скором истечении срока) фоновой службой внутри приложения, запускаемой по расписанию. Фоновые задачи SHALL быть идемпотентными: повторный запуск MUST NOT повторять уже выполненное действие или письмо.

#### Scenario: Плановый запуск

- **WHEN** наступает время планового запуска
- **THEN** служба выполняет задачи и завершает работу без влияния на обработку запросов

#### Scenario: Повторный запуск

- **WHEN** задача запускается повторно после успешного выполнения
- **THEN** повторные действия и письма не создаются

### Requirement: Тестирование

Тесты бэкенда SHALL выполняться командой `dotnet test` и SHALL включать проверки эндпоинтов Web API. Тесты интерфейса SHALL выполняться командой `pnpm test` в каталоге `web`, лежать рядом с проверяемым кодом в каталогах `__tests__` (`web/src/**/__tests__/*.spec.ts`) и SHALL проверять компоненты и клиентские правила. Ни один релиз MUST NOT выполняться при падающих тестах.

#### Scenario: Прогон тестов бэкенда

- **WHEN** разработчик выполняет `dotnet test` в корне решения
- **THEN** запускаются тесты проектов бэкенда и выводится итог по пройденным и упавшим тестам

#### Scenario: Прогон тестов интерфейса

- **WHEN** разработчик выполняет тесты в каталоге `web`
- **THEN** запускаются тесты компонентов и клиентских правил

### Requirement: Окружения и развёртывание

Система SHALL различать окружения через `ASPNETCORE_ENVIRONMENT` (`Development` и `Production`) и SHALL читать настройки из `appsettings` с переопределением через переменные окружения. Развёртывание SHALL выполняться через `docker compose` с сервисами приложения, веб-сервера и PostgreSQL на одном сервере. Секреты MUST NOT храниться в репозитории.

#### Scenario: Локальный запуск

- **WHEN** разработчик поднимает окружение через `docker compose` в режиме разработки
- **THEN** поднимаются приложение, веб-сервер и PostgreSQL, а отладочные возможности доступны

#### Scenario: Производственное окружение

- **WHEN** приложение запущено с окружением `Production`
- **THEN** отладочные возможности и страница-гайд дизайн-системы недоступны

#### Scenario: Откат релиза

- **WHEN** новая версия признана неудачной после развёртывания
- **THEN** развёртывание возвращает предыдущую версию приложения без потери данных

### Requirement: Язык интерфейса и артефактов

Тексты интерфейса, документация и сообщения коммитов SHALL быть на русском языке. Идентификаторы в коде SHALL быть на английском языке: код C# — в стиле `PascalCase`/`camelCase`, компоненты Vue — в стиле `PascalCase` в отдельных файлах.

#### Scenario: Новый текст интерфейса

- **WHEN** в интерфейс добавляется новый пользовательский текст
- **THEN** текст написан по-русски

#### Scenario: Новый идентификатор в коде

- **WHEN** в код добавляется новый идентификатор
- **THEN** он назван по-английски и соответствует стилю своего языка

### Requirement: Ограничения первой версии

Первая версия SHALL обходиться без брокера сообщений, внешнего поискового движка и горизонтального масштабирования. Поиск SHALL выполняться средствами PostgreSQL. Переезд на S3-совместимое хранилище оставлен за рамками первой версии, при этом абстракция хранилища SHALL сохраняться.

#### Scenario: Добавление зависимости первой версии

- **WHEN** рассматривается добавление брокера сообщений или внешнего поискового движка
- **THEN** решение требует отдельного изменения спецификации и не входит в первую версию

#### Scenario: Рост нагрузки на поиск

- **WHEN** поиск начинает требовать внешнего поискового движка
- **THEN** это оформляется отдельным изменением, а PostgreSQL остаётся источником данных
