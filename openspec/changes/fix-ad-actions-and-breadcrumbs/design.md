# Design

## Context

Мотивация — в `proposal.md`. Что важно для реализации:

- `AdService.GetByIdAsync` уже знает зрителя (`viewerId`) и проверяет владение, но `AdSummary`/`AdResponse` не отдают признак авторства, поэтому клиент не может отличить своё объявление от чужого.
- `ComplaintService.FileAsync` требует причину, запрещает жалобы на своё и неактивное объявление, одну жалобу на пользователя; `api.complaints.file(adId, reason)` уже вызывается из клиента.
- В проекте есть образец модального окна на нативном `<dialog>` — `frontend/src/components/PhotoViewer.vue` (открытие `showModal`, Esc/клик вне, возврат фокуса).
- Исправление крошек существует как коммит `a615672` на ветке `remove-non-clickable-breadcrumb-steps`, не влитой в `master`; контент, который он менял в крошках, с тех пор не менялся.

## Goals / Non-Goals

**Goals:**
- Панель действий на странице объявления с корректной видимостью по авторству и статусу.
- Переиспользуемый модальный диалог дизайн-системы и подача жалобы через него.
- Возврат правила «в крошках только кликабельные шаги» и приведение данных крошек на страницах к нему.

**Non-Goals:**
- Изменение API жалоб, редактирования и прав.
- Список готовых причин жалобы — пользователь вводит причину текстом.
- Рефакторинг `PhotoViewer` под общий диалог.
- Прочие действия автора на странице объявления.

## Decisions

### Признак авторства в ответе объявления

`AdSummary` и `AdResponse` получают `IsOwn` (bool). `AdService.GetByIdAsync` заполняет его сравнением `viewerId` с `ad.AuthorId`; в остальных ответах значение по умолчанию `false` (кроме `GetMineAsync`, где объявления заведомо свои — `true`).

**Почему:** клиент показывает «Редактировать» только автору, а сравнивать пользователя с автором без этого поля нечем. Поле аддитивное, схема БД не меняется.

**Альтернативы:** отдельный эндпоинт «моё ли объявление» — лишний запрос; сравнение `id` с выдачей `/ads/mine` — хрупко и избыточно.

### Модальный диалог дизайн-системы

Добавляется переиспользуемый `ModalDialog.vue` на нативном `<dialog>`: заголовок, слот содержимого, действия «подтвердить»/«отмена», закрытие по Esc и клику вне, возврат фокуса. Подача жалобы собирается из него: поле причины и сообщение об ошибке — в слоте. `PhotoViewer` не трогаем.

**Почему:** образец уже есть, нативный `<dialog>` даёт фокус-ловушку и Esc бесплатно; диалог нужен как элемент дизайн-системы под будущие действия.

**Альтернатива:** отдельный `ComplaintDialog.vue` без общего компонента — быстрее, но правило дизайн-системы требует переиспользуемый диалог.

### Видимость действий на странице объявления

- «Редактировать» — ссылка `RouterLink` на `ad-edit`, показывается при `ad.isOwn`.
- «Пожаловаться» — `AppButton`, показывается при активном объявлении и не-своём (`!ad.isOwn`).
- Неавторизованному посетителю «Пожаловаться» ведёт на вход с возвратом на страницу объявления (`redirect`).

Серверная проверка прав сохраняется: клиент лишь скрывает недоступное действие.

### Отправка жалобы

Диалог собирает причину, отправка идёт через `api.complaints.file` в обёртке `useApiAction`. Успех — сообщение и скрытие действия как «подано»; обязательное поле контролируется до отправки; конфликт «жалоба уже отправлена» показывается сообщением сервера через `messageOf`.

### Хлебные крошки

Правило восстанавливается в компоненте: `BreadcrumbItem.to` обязателен, шаг без адреса не рендерится, пустой набор не выводит `<nav>`. Данные крошек приводятся к правилу: `AdDetailView` — «Главная» и подраздел со ссылкой на фильтр; `AdEditView` — без «Редактировать объявление»; админ-разделы — без названия текущего раздела; пример в гайде — без шага без ссылки. Ветка `remove-non-clickable-breadcrumb-steps` удаляется как устаревшая.

**Почему:** повторяет уже проверенное решение `a615672`, но без конфликтов с текущим `master` — часть файлов с тех пор переписана.

## Risks / Trade-offs

- **Появляется поле `IsOwn` в ответе** → аддитивное изменение; обновляются тесты объявлений (`dotnet test`, `pnpm test`).
- **Ветку с исправлением крошек могут случайно влить позже** → после этого изменения удалить локальную и удалённую ветку.
- **Диалог на `<dialog>` в тестах Vitest** (jsdom не умеет `showModal`) → фолбэк на атрибут `open`, как в `PhotoViewer`.
- **Обязательная причина на клиенте и сервере** → сервер остаётся источником правила, клиентская проверка только до отправки.

## Migration Plan

Изменение аддитивное, миграций БД нет. Развёртывание обычное; откат — возврат предыдущей версии без действий с данными.
