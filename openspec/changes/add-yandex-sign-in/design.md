# Design

## Context

Мотивацию смотрите в `proposal.md`. Сейчас техическая форма входа завязана на Google: `users.google_subject` (`character varying(255)`, уникальный индекс), `GoogleAuthService`, статические события `GoogleAuthentication` с временной cookie-схемой `GoogleExternal`, `GoogleSignInOptions.IsConfigured`, эндпоинты `/api/auth/google/{start,link}`, публичный флаг `googleEnabled`, сужение `Set-Cookie` и redirect_uri через `GooglePublicHostMiddleware`. Требования поведения — в дельте `specs/user-accounts/spec.md`.

Ограничение платформы: сущности `Doska.Domain` меняют состояние только через методы, а схема БД — только миграциями EF Core (`openspec/specs/platform/spec.md`). Ввод нового пакета — отклонение, которое надо назвать явно.

## Goals / Non-Goals

**Goals:**

- Идентичность внешнего входа хранится как «провайдер + subject», а не как колонка конкретного сервиса.
- Один провайдеро-агностичный путь разрешения входа/привязки, эндпоинтов и публичных сведений.
- Яндекс ID подключается на этом слое без копирования Google-логики.
- Существующие Google-привязки и текущий вход через Google не теряются и не ломаются.

**Non-Goals:**

- Подключение провайдеров, кроме Google и Яндекса.
- Смена встроенного `AddGoogle` на другой стек и любой переход Google на OIDC.
- Телефон как идентификатор, вход по магической ссылке, OTP, passkeys.
- Отвязка провайдера из интерфейса.

## Decisions

### 1. Таблица `external_logins` вместо колонок субъектов

Вводится сущность `ExternalLogin` (`user_id -> users`, `provider`, `subject`, `created_at`) с уникальностью `(provider, subject)` и `(user_id, provider)`. `User` теряет `GoogleSubject`, `CreateWithGoogle`, `LinkGoogle`, `ApplyGoogleDisplayName`; вместо них общие методы работы с внешней идентичностью.

Почему: `(provider, subject)` — естественный ключ идентичности, он допускает несколько провайдеров на аккаунт и не плодит колонки. Альтернатива — вариант A (клон Google с `yandex_subject`) — быстрее сейчас, но удваивает код и требует третьего клона или рефактора при следующем провайдере; отклонена по требованию «без компромиссов».

### 2. Единый контракт провайдера и общий обработчик тикета

Вводится описание провайдера (`scheme`, отображаемое имя, настройка и признак готовности) и общий обработчик тикета, приводящий данные любого провайдера к контракту `(subject, email, emailVerified, name)`. Унифицированные claim — например `external_subject`, `external_email`, `external_email_verified`, `external_name` — заполняются в `OnCreatingTicket` каждого провайдера, а общий `OnTicketReceived` вызывает `ExternalAuthService`.

Почему: `GoogleAuthentication` уже работает по схеме «временная cookie + нормализованные claim + общий финализатор»; обобщение сохраняет проверенное поведение (CSRF-параметр `state`, correlation-cookie, коды ошибок редиректом).

### 3. `ExternalAuthService` вместо `GoogleAuthService`

Правила разрешения идентичности переносятся как есть, без привязки к Google: сначала поиск по `(provider, subject)`, затем автопривязка по подтверждённому email к аккаунту без привязки этого провайдера, затем создание подтверждённого аккаунта без пароля. Заполнение имени — только если оно не задано. Ошибки — прежние `ServiceErrorKind`.

### 4. Провайдеры: Google остаётся, Яндекс добавляется

- Google — встроенный `Microsoft.AspNetCore.Authentication.Google` (не меняем).
- Яндекс — пакет `AspNet.Security.OAuth.Yandex` из `AspNet.Security.OAuth.Providers`. Яндекс работает по OAuth 2.0 (authorize `oauth.yandex.ru/authorize`, токен `oauth.yandex.ru/token`, профиль `login.yandex.ru/info`) и не является OpenID Connect, поэтому generic-OIDC-клиент не подходит. Обязательный скоуп — `login:email`; отображаемое имя берётся из `real_name`/`display_name`; телефон не запрашивается.
- Email Яндекса считается подтверждённым (требование закрепляет обязательный доступ `login:email`); для Google правило `email_verified` сохраняется.

**Отклонение от `platform`**: добавляется внешняя зависимость. Ограничения первой версии запрещают брокер сообщений и внешний поиск, но не библиотеки аутентификации; добавляем один пакет OAuth-провайдера. Альтернатива — generic `AddOAuth` с ручной реализацией — больше кода и риска рассинхрона с протоколом; отклонена.

### 5. Обобщение инфраструктуры API

- Эндпоинты: `GET /api/auth/{provider}/{start,link}`; callback обслуживает хендлер провайдера; неизвестный или ненастроенный провайдер даёт 404.
- `GET /api/auth/providers` возвращает список `[ { id, name, enabled } ]` вместо булева `googleEnabled`.
- `GooglePublicHostMiddleware` и `GoogleRedirects` переименовываются и обслуживают `/api/auth/*` (пересборка публичного хоста и безопасный локальный возврат).
- Ошибки старта/колбека остаются редиректом с фиксированным кодом; код провайдера добавляется в query (`?<provider>=error&reason=...`).

### 6. Интерфейс

Хранилище `auth` хранит список провайдеров; `LoginView` рисует кнопку на каждого включённого; `ProfileView` показывает текущие привязки и кнопку привязки для каждого доступного провайдера; маппер кодов ошибок ключуется по провайдеру. `PrivacyPolicyView` и `TermsOfServiceView` получают раздел о Яндексе.

### 7. Миграция данных Google

Одна миграция EF Core в этом порядке: создать `external_logins` и её индексы; перенести данные `INSERT ... SELECT id, 'google', google_subject, now() FROM users WHERE google_subject IS NOT NULL`; удалить индекс `ix_users_google_subject` и колонку `google_subject`. `Down` возвращает колонку (nullable), переносит Google-привязки обратно и удаляет таблицу.

## Risks / Trade-offs

- **Потеря Google-привязок при миграции** → перенос данных идёт до удаления колонки, в одной транзакции миграции; существующие API- и unit-тесты входа должны пройти после деплоя.
- **Уникальность `(user_id, provider)`** → исторически у аккаунта одна Google-идентичность, перенос конфликтов не создаёт; нарушитель отсекается индексом.
- **Доверие email Яндекса без флага подтверждения** → принято сознательно; требование обязательно запрашивает `login:email`, а email аккаунта Яндекса — это его контактный адрес.
- **redirect_uri за прокси** (`App` строит его из `Host`) → сохраняем обобщённый middleware; добавить проверку в задаче по prod-конфигурации (порт `:8443`).
- **Верификация и модерация приложения Яндекса** → вне кода; без верификации пользователи видят предупреждение. Учесть в документации деплоя.
- **Совместимость пакета с `net10.0`** → подтвердить версию `AspNet.Security.OAuth.Yandex` при реализации; при отсутствии — временно generic `AddOAuth`.

## Migration Plan

1. Миграция БД: создать `external_logins`, перенести Google, удалить `google_subject`.
2. Задеплоить API с реестром провайдеров; Google-вход работает через новый слой, `GET /api/auth/providers` отдаёт Google.
3. Задать `Yandex__ClientId`/`Yandex__ClientSecret`, перезапустить API — Яндекс появляется в списке.
4. Обновить интерфейс и правовые тексты; `pnpm test` и `dotnet test` зелёные.

Откат: вернуть предыдущий образ API и выполнить `Down` миграции (Google-привязки восстанавливаются из `external_logins`).

## Open Questions

Нет: спорные решения (общий слой, обязательный email, доверие Яндексу, несколько привязок) зафиксированы до design.
