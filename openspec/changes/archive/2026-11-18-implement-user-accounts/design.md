# Design

## Context

См. `proposal.md` — Why. Сейчас:

- `AuthService` умеет регистрировать, входить, подтверждать email и отдавать сведения; `TokenPurpose.PasswordReset` уже объявлен, `UserToken` хранит хеш, срок и момент использования.
- `IEmailSender` и `IPasswordHasher` доступны сценариям; `ValidatePassword` проверяет сложность.
- `UsersController` под политикой «модератор или администратор» умеет выдавать доверие и блокировать; списка пользователей и смены роли нет.
- `AdSearchService` уже исключает объявления заблокированных авторов.

## Goals / Non-Goals

**Goals:**

- Восстановление доступа по одноразовой ссылке без раскрытия существования аккаунта.
- Управление ролями администратором с проверкой на сервере.
- Не менять схему БД и публичные контракты.

**Non-Goals:**

- Смена пароля из кабинета, 2FA, внешние провайдеры, удаление аккаунтов.

## Decisions

### 1. Запрос сброса не раскрывает аккаунт

`RequestPasswordResetAsync(email)` всегда завершается без ошибки. Если пользователь найден, прежние неиспользованные токены `PasswordReset` помечаются использованными, создаётся новый токен со сроком один час и отправляется письмо со ссылкой `/reset-password?token=...`. Для несуществующего адреса ничего не отправляется. Один и тот же ответ сохраняет требование «не раскрывать данные существующего аккаунта».

### 2. Сброс меняет пароль и гасит ссылку

`ResetPasswordAsync(token, password)` проверяет сложность пароля, находит токен по хешу с назначением `PasswordReset`, отвергает отсутствующий, использованный или просроченный, затем записывает новый хеш пароля и помечает токен использованным. Сообщение об ошибке предлагает запросить новую ссылку.

### 3. Роли через отдельный сценарий администратора

`UserService.GetListAsync` возвращает сведения о пользователях для администратора, `ChangeRoleAsync` меняет роль после проверки значения. Права проверяет политика `Admin` на контроллере; роль берётся из записи пользователя при каждом действии, поэтому изменение немедленно влияет на доступ (следующий запрос с cookie получит новую роль при обновлении claims; в первой версии смена роли не переписывает активную сессию).

### 4. API и интерфейс

`/api/auth/forgot-password` и `/api/auth/reset-password` анонимны и ограничены политикой частоты `Sensitive`. `/api/admin/users` и `/api/admin/users/{id}/role` доступны только администратору. Интерфейс получает страницы сброса и список пользователей с выбором роли и блокировкой; блокировка использует существующие эндпоинты `/api/users/{id}/block` и `/api/users/{id}/unblock`.

### 5. Тесты

Интеграционные тесты проверяют: запрос для существующего адреса отправляет письмо, для несуществующего — нет, но ответ одинаковый; использование ссылки меняет пароль и вход с новым паролем работает; повторное использование отклоняется; смена роли доступна администратору и запрещена модератору. Данные помечаются префиксом и удаляются в `DisposeAsync`.

## Risks / Trade-offs

- **Смена роли и активная сессия** → cookie хранит роль на момент входа, поэтому новая роль применится после повторного входа. Это осознанное упрощение первой версии; проверка прав на сервере всё равно опирается на claims сессии.
- **Сброс пароля не отзывает активные сессии** → вне рамок; при необходимости добавляется инвалидация cookie.
- **Письма без ограничения частоты по адресу** → запрос защищён общей политикой частоты по IP.
- **Токен живёт час** → компромисс между безопасностью и удобством; значение вынесено в константу сценария.

## Migration Plan

1. Схема не меняется, миграции не создаются.
2. Проверка: `dotnet build`, тесты бэкенда, `pnpm --dir frontend test`, `pnpm --dir frontend build`.
3. Откат — предыдущая версия; данные совместимы.
