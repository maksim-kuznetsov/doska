# Design

## Context

`AuthService.CreateToken` сейчас генерирует `Convert.ToBase64String(RandomNumberGenerator.GetBytes(32))` и строит ссылку `...?token={rawToken}` без экранирования. `TokenHasher` хранит SHA-256 в hex и не зависит от формата токена. Подтверждение email и сброс пароля используют один генератор. Эндпоинты `AuthController` защищены antiforgery и политикой `Sensitive` (30 запросов в минуту на IP). На фронтенде `ConfirmEmailView` вызывает `POST /api/auth/confirm-email`, а `ForgotPasswordView` — готовый образец формы с нейтральным ответом.

## Goals / Non-Goals

**Goals:**
- Убрать из ссылок символы `+`, `/`, `=`, которые искажают почтовые клиенты.
- Дать пользователю способ получить новое письмо без удаления аккаунта.
- Не раскрывать существование и состояние аккаунта и не позволять спамить чужие ящики.

**Вне рамок:**
- Очередь/outbox и повторные попытки отправки писем.
- Обработка сбоя SMTP при регистрации (аккаунт создаётся, клиент получает 500) — отдельное изменение.
- Смена текста и шаблона писем, провайдера почты, DKIM/SPF.
- Изменение схемы БД.

## Decisions

### 1. Токены в Base64Url

`CreateToken` генерирует токен через `System.Buffers.Text.Base64Url.EncodeToString(RandomNumberGenerator.GetBytes(32))`: 43 символа `A-Z`, `a-z`, `0-9`, `-`, `_`. `TokenHasher` и хранение хеша не меняются, поэтому уже выданные токены продолжают проверяться.

**Почему:** Base64Url не содержит `+`, `/` и `=`, которые ломаются при переносе ссылки и в quoted-printable. Альтернатива — оставить Base64 и только экранировать — отклонена: завершающий `=` уже терялся у реальных почтовых клиентов, а `+` может превратиться в пробел при разборе query-строки.

### 2. Экранирование в ссылке

`BuildLink` формирует параметр как `Uri.EscapeDataString(rawToken)` для подтверждения и сброса пароля.

**Почему:** защита от будущих изменений формата токена и от клиентов, которые повторно декодируют URL. Для Base64Url экранирование ничего не меняет, поэтому ссылки остаются короткими.

### 3. Эндпоинт повторной отправки

`POST /api/auth/resend-confirmation`, `[AllowAnonymous]`, antiforgery, тело `{ email }`, ответ `204 No Content` для любого адреса. Сервис находит пользователя, и письмо уходит только если он существует и `IsEmailConfirmed == false`. Для неизвестного и уже подтверждённого адреса письмо не отправляется, но ответ тот же.

**Почему:** одинаковый ответ не даёт перебирать базу. `204` повторяет поведение `forgot-password`. Текст письма и тема совпадают с регистрационным, чтобы не плодить шаблоны.

### 4. Инвалидация предыдущих ссылок

Перед созданием нового токена все неиспользованные токены подтверждения пользователя помечаются `UsedAt = now`. Действует только ссылка из последнего письма; срок жизни нового токена — те же 24 часа.

**Почему:** одна активная ссылка, как у сброса пароля; старые письма не остаются рабочими навсегда. Компромисс: клик по более раннему письму даёт «ссылка недействительна», поэтому на экране ошибки подтверждения появляется ссылка на повторную отправку.

### 5. Отдельная политика ограничения частоты

Добавляется `RateLimitPolicies.ConfirmationResend`: fixed window, `PermitLimit = 5`, `Window = 15 минут`, `QueueLimit = 0`, разделение по IP. Лимит читается из `RateLimit:ConfirmationResend:PermitLimit` (по умолчанию 5), чтобы тесты могли поднять его, а тест 429 — понизить. Общий лимит `Sensitive` тоже читается из `RateLimit:Sensitive:PermitLimit` (по умолчанию 30), чтобы тестовые сценарии не упирались в него.

**Почему:** общая политика `Sensitive` допускает 30 запросов в минуту — слишком много для писем на чужой ящик. Конфигурируемый лимит убирает зависимость тестов от общего счётчика окна.

### 6. Фронтенд

Новое представление `ResendConfirmationView` и маршрут `/resend-confirmation` по образцу `ForgotPasswordView`: поле email, нейтральное сообщение об успехе, ошибка из `ApiError`. Email подставляется из `auth.user?.email`, если пользователь вошёл. Ссылки добавляются на экран входа («Не пришло письмо подтверждения?») и на экран ошибки подтверждения («Запросить новое письмо»).

**Почему:** пользователь попадает на форму из обоих мест, где узнаёт о проблеме, и не зависит от письма, которое потерялось.

### 7. Тесты

Бэкенд: интеграционные тесты через `ApiFactory` и `CapturingEmailSender` — токен из письма соответствует `^[A-Za-z0-9_-]{43}$`, подтверждение работает, повторное отклоняется, повторная отправка инвалидирует старый токен, неизвестный и подтверждённый email не получают письмо, превышение лимита даёт 429. `ApiFactory` задаёт высокий лимит для обычных тестов, тест 429 использует отдельную фабрику с лимитом 2. Фронтенд: Vitest для `ResendConfirmationView` и ссылки на повторную отправку в `ConfirmEmailView`.

**Почему:** проверяется наблюдаемое поведение из дельты спецификации, а не внутренний формат.

## Risks / Trade-offs

- **Старые ссылки с `+`, `/`, `=` остаются нерабочими** → после релиза пользователь запрашивает новое письмо; новые токены URL-safe.
- **Инвалидация старых ссылок при повторной отправке** → на экране ошибки есть переход к повторной отправке; в письме действует последняя ссылка.
- **Одинаковый ответ всё равно может различаться по времени** (отправка письма дольше) → для v1 принимаем: лимит частоты снижает ценность перебора, тело и код ответа не различаются.
- **Лимит по IP затрагивает пользователей за общим NAT** → 5 запросов за 15 минут достаточно для обычного сценария; лимит настраивается.
- **Синхронная отправка SMTP** → запрос ждёт провайдера; токен создаётся до отправки, поэтому повторный запрос после ошибки создаст новую ссылку. Очередь — вне рамок.

## Migration Plan

1. Выпустить бэкенд и фронтенд; миграция БД не нужна.
2. Проверить: регистрация даёт 43-символьный токен без `+`, `/`, `=`; ссылка подтверждает аккаунт; повторная отправка присылает новое письмо; неизвестный адрес получает `204` без письма; шестой запрос за 15 минут — `429`.
3. Откат — возврат предыдущей ревизии кода. Уже выданные токены остаются валидными: хеш не зависит от формата. Данные не мигрируются.
