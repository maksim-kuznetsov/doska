# Design

## Context

См. `proposal.md` — Why. Что важно для подхода:

- Сущности уже содержат доменные методы с правилами, но свойства объявлены `{ get; set; }`, поэтому правила обходятся (`AdService.UpdateAsync` пишет поля напрямую, `UserService.ChangeRoleAsync` — `user.Role`, сидеры — `new Category { ParentId = … }`).
- Отметки времени сейчас проставляет `AppDbContext.ApplyTimestamps` через `TimeProvider`; домен системные часы не использует.
- Сервисы уже получают `TimeProvider` (`clock`) и в части методов передают `now` в домен (`Ad.Approve(now)`, `User.Block(now)`, `AdComplaint.Close(now)`).
- Тела запросов и ответов не переиспользуют сущности, поэтому закрытие сеттеров контракт API не затрагивает.

## Goals / Non-Goals

**Goals:**
- Состояние сущностей `Doska.Domain` меняется только доменными методами; прямой записи извне нет.
- Создание — только через конструктор с обязательными данными.
- Домен сам владеет `CreatedAt`/`UpdatedAt`; слой доступа к данным отметки не проставляет.
- Существующие правила (`Approve`, `SetParent`, `Rename` и т. д.) становятся единственным путём изменения состояния.

**Non-Goals:**
- Изменение схемы БД и миграции.
- Изменение контрактов Web API и бизнес-текстов.
- Оптимистичная блокировка, интерсепторы и страховки от забытого `UpdatedAt`.
- Пересмотр самих бизнес-правил (только способ доступа к состоянию).

## Decisions

### D1. Создание через параметризованный конструктор

Новые сущности создаются конструктором с обязательными данными; для материализации EF Core добавляется приватный конструктор без параметров.

- **Почему:** конструктор делает обязательные данные обязательными по типу и исключает состояние «создано, но не настроено». Логика статуса по доверию автора переезжает в конструктор `Ad` — сейчас она продублирована в `AdService.CreateAsync` и в методах `Ad`.
- **Альтернативы:** публичные `init`-сеттеры (оставляют возможность частично собранного объекта и не выражают обязательность); фабричные методы (лишний слой при уже готовых конструкторах).

### D2. Домен владеет временем

Конструкторы и мутирующие методы принимают `now` и сами проставляют `CreatedAt`/`UpdatedAt`. `AppDbContext` теряет `TimeProvider`, `ApplyTimestamps` и оба override `SaveChanges`.

- **Почему:** отметки времени становятся частью состояния, которым владеет домен; убирается запись из Infrastructure в сущность, из-за которой и появился бы шов вроде `Touch()`.
- **Альтернативы:** `Touch(now)` (доменный API ради персистентности); `internal set` + `InternalsVisibleTo`; запись через EF-метаданные (`entry.Property(...).CurrentValue`). Отклонены: либо не закрывают модель, либо добавляют концепт без потребителя.
- **Следствие:** `AppDbContextFactory` и конструирование контекста в тестах упрощаются до `new AppDbContext(options)`.

### D3. Закрытые сеттеры и коллекции

Свойства состояния — `private set`; коллекции — доступны только на чтение (EF Core дополняет существующую коллекцию); навигационные ссылки — `private set`. `Id` — `private set` со значением по умолчанию (EF Core перезаписывает при материализации).

- **Почему:** это и есть цель изменения — правила нельзя обойти.
- **Альтернативы:** оставить `public set` (текущее состояние, правила обходятся).

### D4. Доменные методы для операций, выполняемых сейчас напрямую

Добавляются методы, заменяющие прямую запись: `User.ChangeRole`, `User.SetPassword`, `User.ConfirmEmail`, `UserToken.MarkUsed`, `Ad.UpdateDetails`, `Ad.MarkReminderSent`. В существующие методы без `now` (`Ad.CompleteEdit/MarkSold/Archive/Hide/Reject`, `User.RegisterApprovedAd/GrantTrust/RevokeTrust/Unblock`, `Category.Rename/SetSortOrder/Activate/Deactivate/SetParent`, `City.Rename/Activate/Deactivate`) добавляется `now`.

- **Почему:** каждая запись состояния получает имя и место, где живёт правило, включая обновление `UpdatedAt`.
- **Альтернативы:** оставить часть изменений в сервисах (тогда сеттеры пришлось бы оставить открытыми).

### D5. Тесты и сидеры

Сущности в тестах создаются общим тестовым билдером (один на сущность), доменные тесты переходят на конструкторы и методы. Сидеры получают `TimeProvider` параметром (как сервисы), чтобы время оставалось подменяемым.

- **Почему:** ~55 мест в тестах и 4 сидера строят сущности напрямую; без билдера и параметра времени они не соберутся.
- **Альтернативы:** оставить тестам исключения (потребовало бы `InternalsVisibleTo` и открытых сеттеров — противоречит цели).

## Risks / Trade-offs

- **Забытый `UpdatedAt` в новом методе** → метка молча не обновится. Митигация: все мутации идут через методы (D3/D4), обновление `UpdatedAt` видно в ревью; страховка не добавляется осознанно.
- **Материализация EF Core при закрытых конструкторах/сеттерах** → нужен приватный конструктор без параметров; проверяется тестами чтения сущностей из базы.
- **BREAKING для внутреннего API кода** → все вызовы (сервисы, сидеры, тесты) переводятся в одном изменении; частичный перевод не собирается.
- **Объём правок в тестах** → билдеры (D5) снижают дублирование; это основная часть работы, а не сами сущности.
- **Два источника времени у одной операции** → сервис берёт `now` один раз и передаёт в метод; повторный вызов `clock` не допускается.

## Migration Plan

1. Изменить сущности (конструкторы, `private set`, `now` в методах, новые методы).
2. Убрать штамповку из `AppDbContext`, упростить `AppDbContextFactory`.
3. Перевести сервисы на методы/конструкторы, сидеры — на `TimeProvider`.
4. Перевести тесты на билдеры; переписать `SaveChangesTests` под владение временем доменом.
5. Проверка: `dotnet test` из `backend` — зелёный.

Миграций БД нет, схема не меняется. Откат — реверт изменения; данные и контракт API не затрагиваются.

## Open Questions

- Точные сигнатуры конструкторов и набор параметров для каждой сущности — уточняются при реализации, на подход и задачи не влияют.
