# Design

## Context

See `proposal.md` — Why. Текущее состояние:

- Вход выдаёт зашифрованный cookie-тикет с claims `sub`, `email`, `role` (`AuthController.SignInAsync`).
- Авторизация строится на `ClaimTypes.Role`; политики `ModeratorOrAdmin` и `Admin`.
- `AdminUsersController` меняет `User.Role`, `UsersController` блокирует пользователя, но cookie не перевыпускается.
- `IAppDbContext` доступен как scoped-сервис; `OnValidatePrincipal` может получить его из `RequestServices`.

## Goals / Non-Goals

**Goals:**

- Применять актуальную роль и блокировку к каждому авторизованному запросу.
- Не менять схему и не добавлять миграции.

**Non-Goals:**

- Мгновенный отзыв сессии при смене пароля.
- Кэш между запросами и фоновая инвалидация.

## Decisions

### 1. Перестроение principal в `OnValidatePrincipal`

При каждом запросе cookie-обработчик вызывает `OnValidatePrincipal`: сценарий загружает пользователя по `sub` (`AsNoTracking`), проверяет отсутствие/блокировку и создаёт новый `ClaimsPrincipal` с текущими `email` и `role`, после чего вызывает `ReplacePrincipal`. Авторизация и контроллеры видят новые права в том же запросе. Альтернатива — `SecurityStamp` в БД и сверка метки: требует колонки, миграции и обновления метки во всех сценариях изменения роли/блокировки; для текущего объёма это лишняя сложность.

### 2. Заблокированный или удалённый пользователь — отказ и удаление cookie

Если записи нет или `BlockedAt` заполнен, вызывается `RejectPrincipal` и `SignOutAsync`, поэтому текущий запрос завершается как неаутентифицированный (401), а браузер теряет cookie. Это закрывает доступ заблокированного пользователя без ожидания истечения сессии.

### 3. Один запрос к БД на авторизованный запрос

Проверка выполняется на каждом запросе с `AsNoTracking`, без кэша: роль должна применяться немедленно. Для масштаба первой версии один индексный запрос по первичному ключу приемлем; при росте можно добавить короткий кэш или `SecurityStamp` с инвалидацией.

### 4. Смена роли не перевыпускает cookie

Principal заменяется только в памяти запроса; сам тикет остаётся прежним. Это осознанно: cookie не содержит актуальной роли, и её значение не используется. Перевыпуск на каждое изменение не нужен, а `SlidingExpiration` и так обновляет срок.

## Risks / Trade-offs

- **Дополнительный запрос к БД на каждый авторизованный запрос** → приемлемо для текущей нагрузки; при необходимости добавляется кэш.
- **Отказ при недоступной БД** → fail closed: запрос завершается 401, а не работает со старыми правами.
- **Cookie может содержать устаревшую роль** → она игнорируется, потому что principal всегда перестраивается.

## Migration Plan

1. Схема не меняется, миграции не создаются.
2. Проверка: сборка, тесты бэкенда, тесты интерфейса.
3. Откат — предыдущая версия; поведение сессий возвращается к прежнему.
