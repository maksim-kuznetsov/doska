# Design

## Context

См. `proposal.md` — раздел «Why». Существенное для подхода:

- Репозиторий пустой: есть только `openspec/` (10 спецификаций, справочник — `openspec/specs/platform/spec.md`) и `.git`. Ни решения, ни `package.json`, ни конфигурации окружения.
- Текущая спецификация `platform` требует `Doska.sln` в корне и каталог `web`; согласованное решение — `backend/` и `frontend/`. Отклонение названо явно и снимается дельтой спеки в этом же изменении.
- Машина разработчика: Windows, PowerShell 5.1, без bash-синтаксиса. `pnpm` в системе отсутствует (согласована установка через `corepack`).
- Первая версия по `platform` работает без брокера сообщений, внешнего поиска и S3; медиафайлы — через абстракцию хранилища.

## Goals / Non-Goals

**Goals:**

- Каркас, который запускается целиком на локальной машине: PostgreSQL в контейнере, API со Swagger, dev-сервер интерфейса с проксированием `/api`.
- Проверяемость: `dotnet test` из `backend`, `pnpm test` в `frontend`, `docker compose up -d postgres` дают воспроизводимый результат сразу после `apply`.
- Согласованность спецификаций: дельты приводят `platform`, `user-accounts`, `static-assets`, `design-system` к новой структуре.

**Non-Goals:**

- Сущности EF Core, миграции и их применение при старте — каркас остаётся пустым.
- Бизнес-эндпоинты, аутентификация, страницы интерфейса сверх проверочного минимума.
- Продакшн-развёртывание: полный `docker compose` (api + web/nginx + postgres), HTTPS, CI — отдельные изменения.

## Decisions

### 1. Каталоги `backend/` и `frontend/` вместо корневого решения и `web/`

Решение: решение живёт в `backend/Doska.sln`, интерфейс — в `frontend/`. Каталог `web` не создаётся.

Почему: два стека не смешиваются в корне, каждая часть ставится и собирается своей командой. Отклонение от `platform` фиксируется дельтой (требования «Структура репозитория» и «Тестирование»), пути `web/...` в трёх других спеках приводятся к `frontend/...`, иначе спецификации противоречат коду.

Альтернатива — оставить `web/` и корневое решение: отвергнута, так как выбрана раскладка по стекам.

Допущение: имена проектов сохраняются (`Doska.Domain`, `Doska.Application`, `Doska.Infrastructure`, `Doska.Api`, `tests/Doska.Tests`), меняется только их расположение внутри `backend/`.

Ограничение инструмента: блок `MODIFIED` в дельта-спеке заменяет требование целиком, и `openspec validate` не принимает переименование или удаление сценариев. Поэтому сценарий требования «Структура репозитория» сохраняет прежнее название «Состав каталога web», хотя описывает уже каталог `frontend`; пути в его тексте даны полностью (`frontend/src/...`) и двусмысленности не создают.

### 2. Полная слоистая раскладка сразу

Решение: создаются все четыре проекта и тестовый. Направление ссылок: `Domain` ← `Application` ← `Infrastructure` ← `Api`; тесты ссылаются на `Api` (и через него на остальные). `Domain` не ссылается ни на что.

Почему: структура уже зафиксирована в `platform`, а перенос кода из одного проекта в пять позже дороже, чем завести пустые проекты сейчас.

Альтернатива — одно приложение `Doska.Api` с последующим разделением: отвергнуто, противоречит требованию «Структура репозитория».

### 3. Пустой `AppDbContext` и отложенное применение миграций

Решение: `AppDbContext` объявляется в `Doska.Infrastructure`, регистрируется через `AddDbContext` с `UseNpgsql` и `UseSnakeCaseNamingConvention`; сущностей и миграций нет, `Database.Migrate()` при старте не вызывается.

Почему: изменение не принимает решений о модели данных; при нуле миграций применять нечего, а вызов миграции при старте делал бы проверочный тест API зависимым от живой базы. Требование `platform` о применении миграций до обслуживания запросов выполняется тем изменением, которое вводит первую миграцию (ожидаемо — `user-accounts`).

Альтернатива — демонстрационная сущность и миграция: отвергнута, чтобы не тащить временную модель данных.

### 4. Строка подключения и секреты

Решение: строка `ConnectionStrings:Default` для локальной разработки — в `backend/src/Doska.Api/appsettings.Development.json` и указывает на контейнер из `docker-compose.yml` (`Host=localhost;Port=5433;Database=doska;Username=doska;Password=doska`). Порт 5433 выбран потому, что 5432 на машине разработчика занят запущенным стеком предыдущей версии проекта (`doska-db-1` в `C:\Projects\doska`); порт хоста для контейнера — единственное расхождение с исходной формулировкой задачи 4.1, зафиксированное решением владельца при выполнении. Для остальных окружений строка приходит из переменных окружения; пароль контейнера локальной разработки не является секретом репозитория.

Почему: соответствует требованию `platform` «секреты не хранятся в репозитории» — в репозитории только учётные данные одноразового локального контейнера.

### 5. Swagger ищется в `Development`, контроллеры, `ProblemDetails`

Решение: `AddControllers()` + атрибутные контроллеры (никаких Minimal API), `AddProblemDetails()` для единого формата ошибок, Swashbuckle (`AddSwaggerGen`, `UseSwagger`/`UseSwaggerUI` на `/swagger`) только при `IsDevelopment()`. Добавляется проверочный эндпоинт `GET /api/health`, возвращающий окружение и версию сборки.

Почему: `platform` описывает `Doska.Api` как контроллеры и требует `ProblemDetails`; проверочный эндпоинт даёт предмет для теста API, проверки CORS и прокси и не относится к бизнес-логике. Документация доступна только в разработке, чтобы не публиковать её в продакшне.

Альтернатива — встроенный `Microsoft.AspNetCore.OpenApi` без UI: отвергнута, так как запрошен именно Swagger с browsable-интерфейсом.

### 6. CORS только для dev-сервера и только в `Development`

Решение: политика `FrontendDev` с явным списком источников (`http://localhost:5173`, `http://127.0.0.1:5173`) и разрешёнными учётными данными (`AllowCredentials`), подключается только при `IsDevelopment()`.

Почему: `platform` использует cookie-сессию `httpOnly` и antiforgery, поэтому `AllowAnyOrigin` недопустим в принципе, а в продакшне интерфейс и API отдаёт один сервер и CORS не нужен. Основной поток разработки идёт через прокси Vite и остаётся одного источника; CORS нужен для прямых обращений браузера и инструментов.

### 7. Прокси Vite на бэкенд

Решение: в `frontend/vite.config.ts` — `server.proxy: { '/api': { target: 'http://localhost:5000', changeOrigin: true } }`, порт dev-сервера 5173. Адрес API в коде интерфейса — относительный (`/api/...`).

Почему: относительные адреса не требуют переменных окружения на фронтенде и сохраняют cookie-сессию в одном источнике, как в продакшне.

### 8. `docker-compose.yml` с одним сервисом PostgreSQL

Решение: файл в корне проекта, сервис `postgres` (`postgres:17-alpine`, база `doska`, пользователь `doska`, постоянный том, `healthcheck` через `pg_isready`, публикация `5433:5432`). На хосте выбран порт 5433: 5432 занят старым стеком `doska`, и поднимать два стека одновременно удобнее, чем останавливать существующее окружение. Ключ `version` не указывается.

Почему: локальной разработке нужна только база; API и интерфейс удобнее запускать из терминала с горячей перезагрузкой. Том сохраняет данные между перезапусками, healthcheck не даёт бэкенду подключаться к ещё не готовой базе.

### 9. `pnpm` через corepack, тесты — Vitest

Решение: `corepack enable pnpm`, затем `pnpm install`; в `frontend/` — Vue 3, TypeScript, Vite, Pinia, `vue-router` (маршруты нужны требованием «Состав каталога frontend») и Vitest с `@vue/test-utils`. Поле `packageManager` в `package.json` не фиксируется.

Почему: согласовано с владельцем проекта, отдельная установка Node-менеджеров не требуется. В используемой версии Node (26.13.1) `corepack` не поставляется, поэтому он ставится глобально через `npm`, а `pnpm` — уже через `corepack`; это подтверждено владельцем при выполнении задачи 5.1. Проверочные тесты интерфейса — один тест на монтирование корневого компонента с Pinia, лежит в `frontend/src/**/__tests__/*.spec.ts`.

## Risks / Trade-offs

- [Порты 5000, 5173, 5432 заняты другой программой] → задачи проверяют занятость портов до запуска (`Get-NetTCPConnection`), порты собраны в одном месте документации и меняются синхронно (`launchSettings.json`, `vite.config.ts`, `docker-compose.yml`, `appsettings.Development.json`). Риск реализовался на порту 5432: его занимает старый стек `doska`, поэтому контейнер публикуется на 5433.
- [Docker Desktop не запущен, `docker compose up` падает] → задача проверяет `docker info` и сообщает о необходимости запустить Docker, не считая это дефектом каркаса.
- [`corepack enable pnpm` требует прав на запись в каталог Node] → выполняется один раз, при отказе доступа задача останавливается и сообщает о проблеме, установка обходными путями не делается. Риск реализовался иначе: в Node 26.13.1 `corepack` не поставляется вовсе, поэтому по решению владельца `corepack` ставится глобально через `npm install -g corepack`, после чего выполняется `corepack enable pnpm`.
- [Каркас отклоняется от `platform` и спеки расходятся] → дельты в этом же изменении приводят четыре спецификации к новой структуре; после `apply` изменение архивируется, и `openspec validate` остаётся зелёным.
- [Отложенное применение миграций выглядит как невыполненное требование `platform`] → решение зафиксировано в design и в тексте дельты; первая миграция добавляет вызов применения при старте.
- [Версии шаблонов `dotnet new` и пакетов Node со временем меняются] → версии пакетов .NET фиксируются в файлах проектов, версии интерфейса — в `pnpm-lock.yaml`, который коммитится.
- [Интерфейс без бизнес-страниц может не покрыть требования `design-system`] → это вне рамок изменения: каркас создаёт каталоги и точку входа, наполнение — отдельные изменения.

## Migration Plan

Изменение только добавляет файлы: `backend/`, `frontend/`, `docker-compose.yml` и правки документации OpenSpec. Данных и пользователей нет, миграция схемы не требуется. Откат — удалить добавленные каталоги и файл, вернуть дельты (изменение не архивируется). Порядок применения — порядок задач в `tasks.md`: бэкенд, локальная база, интерфейс, связка и проверки.

## Open Questions

- Фиксировать ли версию `pnpm` полем `packageManager` — можно решить при появлении второй среды разработки, на каркас и задачи не влияет.
- Нужен ли HTTPS-профиль API для локальной разработки сверх http — решение не меняет ни спецификации, ни состав задач.
