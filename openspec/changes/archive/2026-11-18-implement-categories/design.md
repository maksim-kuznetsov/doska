# Design

## Context

See `proposal.md` — Why. Текущее состояние:

- `Category` уже хранит `Name`, `ParentId`, `IsActive`, `SortOrder`; `SetParent` запрещает третий уровень и родителя-самого-себя.
- В БД есть уникальный индекс по `name` и `CHECK (sort_order >= 0)`; имя категории уникально глобально, а не внутри раздела.
- Публичный справочник `GET /api/catalog/sections` уже отдаёт активные разделы с активными подразделами; `AdService` принимает только активный подраздел.
- Политика `Admin` уже настроена.

## Goals / Non-Goals

**Goals:**

- Дать администратору полный жизненный цикл категории без изменения схемы.
- Соблюсти правила: два уровня, уникальное имя, неотрицательный порядок, запрет удаления используемой категории.
- Показать посетителю дерево активных категорий в шапке и вести к ленте выбранного подраздела.

**Non-Goals:**

- Города, объявления и другие сущности в админке.
- Drag-and-drop и пакетное переупорядочивание.
- Иконки и изображения категорий.

## Decisions

### 1. Операции — методы домена, сценарии — оркестрация

В `Category` добавляются `Rename`, `SetSortOrder`, `Activate`, `Deactivate` и фабрики `CreateSection`/`CreateSubsection`. Фабрики используют существующий `SetParent`, поэтому правило двух уровней остаётся в одном месте. Сценарий `CategoryService` проверяет уникальность имени и наличие объявлений/подразделов, затем вызывает метод и сохраняет изменения.

### 2. Уникальность имени проверяется заранее

Имя категории уникально глобально (индекс БД). Сценарий ищет категорию с таким же именем (кроме редактируемой) и возвращает 409 с понятным текстом вместо 500 от ограничения БД. Альтернатива — ловить `DbUpdateException`: даёт менее понятное сообщение и зависит от провайдера.

### 3. Удаление только пустой категории

Удаление запрещено, если у категории есть объявления или подразделы. В ответе 409 предлагается деактивировать. Это выполняет требование `categories` и не создаёт висящих ссылок; каскадное удаление объявлений недопустимо.

### 4. Деактивация не скрывает существующие объявления

Деактивированный подраздел исчезает из публичного дерева и из выбора при подаче, но объявления в нём остаются в общей ленте и поиске — так требует `categories`. Поэтому публичное дерево фильтрует `IsActive`, а базовая выдача объявлений — нет. При этом фильтр по разделу верхнего уровня учитывает только активные подразделы, а прямой выбор подраздела в ленте остаётся доступным и после деактивации.

### 5. Админские эндпоинты отдельно от публичного справочника

Публичное дерево остаётся в `GET /api/catalog/sections`; управление — в `GET/POST/PUT/DELETE /api/admin/categories` под политикой `Admin`. Публичный справочник не показывает неактивные элементы и не требует входа. Отдельный префикс упрощает права и не смешивает чтение и запись.

### 6. Порядок вывода — целое число

`SortOrder` задаётся числом `>= 0` при создании и редактировании; сортировка раздела — `SortOrder`, затем имя. Drag-and-drop не реализуется, чтобы не усложнять интерфейс первой версии.

### 7. Дерево в шапке — отдельный компонент

`CategoryMenu.vue` получает список разделов пропом и отвечает только за раскрытие/закрытие и ссылки. Загрузку делает раскладка. Это упрощает тест компонента без сети. Выбор подраздела ведёт на `/?categoryId=<id>`, который уже понимает лента.

## Risks / Trade-offs

- **Глобальная уникальность имени** → одинаковые названия подразделов в разных разделах невозможны; это ограничение существующей схемы, проверяется заранее и сообщается пользователю.
- **Нет пакетного переупорядочивания** → администратор меняет порядок по одному; для первой версии достаточно.
- **Кэширование публичного дерева отсутствует** → дерево запрашивается при загрузке страницы; объём справочника мал.
- **Удаление категории между проверкой и сохранением** → гонка возможна, но админские операции редки; ограничение БД всё равно не даст удалить связанную запись.

## Migration Plan

1. Схема не меняется, миграции не создаются.
2. Проверка: `dotnet build`, тесты бэкенда, `pnpm test`, `pnpm build`.
3. Откат — предыдущая версия; данные совместимы.
