# Design

## Context

См. `proposal.md` — Why. Сейчас:

- `docker-compose.yml` поднимает только PostgreSQL для разработки; API и dev-сервер запускаются на хосте.
- `MediaController` в `Production` отвечает `X-Accel-Redirect: /media-internal/photos/...`; веб-сервера, который обрабатывает этот путь, нет.
- Настройки читаются из `appsettings` с переопределением переменными окружения; `ConnectionStrings:Default` в `Development` задан, для `Production` строки нет.
- `AdsController.Create` уже ограничен политикой `Sensitive`; аутентификация, antiforgery, миграции при старте и фоновые задачи реализованы.

## Goals / Non-Goals

**Goals:**

- Дать воспроизводимое производственное развёртывание на одном сервере.
- Описать откат релиза без потери данных.
- Не хранить секреты в репозитории.
- Сохранить существующую архитектуру и код приложения.

**Non-Goals:**

- CI/CD, Kubernetes, балансировка, секрет-менеджер, HTTPS-сертификаты.

## Decisions

### 1. Три сервиса в `docker-compose.prod.yml`

`postgres` — база с постоянным томом; `api` — образ приложения, окружение `Production`, строка подключения и параметры медиа из переменных окружения, общий том медиа; `web` — nginx с собранным интерфейсом, публикует порт и проксирует `/api` на `api`. Веб-сервер остаётся единственной точкой входа, поэтому медиа в `Production` отдаёт nginx по внутреннему пути.

### 2. nginx: SPA, API и медиа

`deploy/nginx.conf` обслуживает `index.html` через `try_files` (клиентская маршрутизация), проксирует `/api/` на сервис `api` и отдаёт `/media-internal/` из тома медиа как `internal`, чтобы к нему нельзя было обратиться снаружи. Заголовки кеширования добавляются в change `static-assets`; здесь закладывается только базовая отдача.

### 3. Секреты через переменные окружения

`docker-compose.prod.yml` читает `POSTGRES_PASSWORD` и строку подключения из окружения (файл `.env`), `.env.example` показывает имена переменных без значений, `.env` исключён из git. Так секреты не попадают в репозиторий, а окружения различаются значением `ASPNETCORE_ENVIRONMENT`.

### 4. Миграции и откат

API применяет миграции при старте и при ошибке не начинает обрабатывать запросы — контейнер не становится здоровым, и развёртывание не переключается. Откат — вернуть предыдущий образ (`docker compose -f docker-compose.prod.yml up -d` из предыдущей ревизии); данные остаются в томах, схема совместима в обе стороны, потому что миграции аддитивны.

### 5. Манифест сборки

`vite.config.ts` включает `build.manifest`, поэтому каталог сборки содержит манифест с хешированными именами ассетов, а `index.html` ссылается на них. Это выполняет требование «подключение по манифесту» и готовит почву для кеширования в `static-assets`.

### 6. Тест конфигурации

Тест интерфейса читает `docker-compose.prod.yml`, `deploy/nginx.conf` и `.env.example`: проверяет три сервиса, проксирование `/api`, внутренний путь медиа и отсутствие значений секретов. Так конфигурация развёртывания защищена от случайного удаления.

## Risks / Trade-offs

- **Один сервер** → нет горизонтального масштабирования; это осознанное ограничение первой версии.
- **Том медиа общий для api и web** → nginx читает файлы только на чтение; при переезде на S3 меняется только реализация хранилища.
- **Откат вручную** → автоматического отката нет; шаги описаны в README.
- **Тест читает файлы репозитория** → зависит от структуры каталогов; путь вычисляется от каталога фронтенда, где запускаются тесты.

## Migration Plan

1. Схема БД не меняется.
2. Развёртывание: заполнить `.env`, выполнить `docker compose -f docker-compose.prod.yml up -d --build`.
3. Проверка: `dotnet build`, тесты бэкенда, `pnpm --dir frontend test`, `pnpm --dir frontend build`.
4. Откат: вернуть предыдущую ревизию и повторить `up -d --build`; тома сохраняются.
