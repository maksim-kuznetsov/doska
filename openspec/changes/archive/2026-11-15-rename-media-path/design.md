# Design

## Context

Фото и миниатюры сейчас получают имена в `src/Doska.Infrastructure` через `IFileStorage` (`ads/<ad_id>/...`). В базе хранятся относительные имена, представления строят адрес от базового пути `/media/`, nginx отдаёт `/media/` из локального тома. Данные уже есть: два объявления с файлами в `ads/1/...` и `ads/2/...`. См. `proposal.md` — Why.

## Goals / Non-Goals

**Goals:**

- Новые загрузки идут в `photos/...` без сегмента, который режут блокировщики.
- Существующие файлы и записи переводятся на новый путь без потери фото.
- Миграция EF Core безопасна при повторном запуске и не зависит от реализации `IFileStorage`.

**Non-Goals:**

- Менять имена файлов, структуру каталогов по объявлениям или размеры изображений.
- Чистить осиротевшие файлы, на которые нет записей `AdPhoto`.
- Хранить копии по старому пути: совместимость адресов обеспечивают правила маршрутизации nginx.

## Decisions

- **Новый префикс `photos/` вместо маскировки (`files/`, `img/`).** Понятное имя, не пересекается с фильтрами `ads`; альтернативные префиксы не дают преимуществ.
- **Копирование и удаление через `IFileStorage`, а не перемещение средствами файловой системы.** Работает и на локальном томе, и на S3-совместимом хранилище после переезда; цена — кратковременное удвоение размера файла, для фото до 5 МБ это допустимо.
- **Имя в новом каталоге выводится из старого** (`ads/<...>` → `photos/<...>`), поэтому структура `thumbs/` и UUID сохраняются, а миграция остаётся простой и предсказуемой.
- **Идемпотентность на уровне записи.** Если исходного файла нет — запись пропускается; если целевой файл уже существует — копирование пропускается, но имя в базе обновляется. Повторный запуск не ломает данные.
- **Обратная миграция** переносит `photos/` → `ads/` тем же алгоритмом, чтобы откат кода не оставлял битые ссылки.
- **Совместимость старых адресов.** Правила маршрутизации nginx перенаправляют `/media/ads/...` на новый путь, поэтому ранее опубликованные адреса продолжают отдавать файлы после переноса.

## Risks / Trade-offs

- [Миграция падает посередине] → файл сначала копируется, затем сохраняется имя, и только потом удаляется исходник; при ошибке копии запись остаётся на старом пути, а сервис `api` не стартует, сигнализируя проблему.
- [Не хватает места на диске] → кратковременно заняты обе копии; на VPS 10 ГБ и фото до 5 МБ это единицы мегабайт на объявление; при нехватке — освободить образы (`docker image prune`).
- [Блокировщик режет и `photos`] → маловероятно, но проверка в браузере с включённым блокировщиком входит в задачи.
- [Браузер кэшировал старые адреса] → разметка SPA не кэшируется надолго, после перезагрузки страницы ссылки новые; старые адреса продолжают отвечать за счёт совместимости маршрутов.
- [Осиротевшие файлы остаются в `ads/`] → вне области изменения; при необходимости чистятся вручную.

## Migration Plan

1. Снять бэкап (`deploy/backup.sh`).
2. Выкатить релиз: `docker compose up -d --build`; миграция EF Core `MoveMediaToPhotos` применяется при развёртывании командой `dotnet ef database update --project src/Doska.Infrastructure --startup-project src/Doska.Api` до запуска обработки запросов.
3. Проверить: в `/data/media/photos/` есть файлы, в базе имена начинаются с `photos/`, изображения открываются, старые адреса `/media/ads/...` по-прежнему отдают файлы.
4. Откат: применить предыдущую миграцию EF Core (`dotnet ef database update <ПредыдущаяМиграция>`) — файлы и имена вернутся в `ads/`, затем вернуть предыдущий коммит и пересобрать контейнер.
