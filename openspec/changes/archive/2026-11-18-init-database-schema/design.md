# Design

## Context

См. `proposal.md` — «Why». Здесь только то, что определяет подход:

- `AppDbContext` пуст (изменение `setup-base-architecture` намеренно оставило его без наборов сущностей), каталога `Migrations` нет, в базе нет таблиц.
- Строка подключения уже настроена: `UseNpgsql(...).UseSnakeCaseNamingConvention()` в `Program.cs`, локальная база — `docker compose`, порт хоста 5433.
- `Database.Migrate()` при старте намеренно не вызывался; требование `platform` «Применение миграций» ждёт первую миграцию.
- `Doska.Domain` не имеет ссылок ни на один проект, поэтому сущности могут использовать только BCL.
- Спецификации задают статусы, счётчики и связи, но не задают типы данных и длины строк — их выбираем здесь и фиксируем как допущения.

## Goals / Non-Goals

**Goals:**

- Одна миграция `InitialSchema`, полностью описывающая схему, необходимую сценариям всех спецификаций `openspec/specs/`.
- Сущности без поведения, пригодные для сценариев использования в `Doska.Application`: правила (лимиты, автоархив, доверие) считаются по этим данным, но здесь не реализуются.
- Схема сама защищает инварианты, которые выражаются в PostgreSQL: неотрицательная цена, диапазон статусов, не более пяти фото.

**Non-Goals:**

- Репозитории, сценарии использования, DTO, эндпоинты, аутентификация — следующих изменений.
- Таблица сессий: способ хранения cookie-сессии (ticket через Data Protection или таблица) решает изменение аутентификации, схему под него здесь не вводим.
- Начальные данные (города, категории, демо-аккаунты).
- Полнотекстовый поиск: `ad-search` требует подстроку без учёта регистра, а не поиск по словам.

## Decisions

### 1. Модель данных

Семь сущностей, по одной таблице на каждую; подраздел и раздел — одна таблица с самоссылкой.

| Сущность | Таблица | Ключевые поля | Ограничения |
| --- | --- | --- | --- |
| `User` | `users` | `email`, `password_hash`, `role`, `is_email_confirmed`, `is_trusted`, `approved_ads_count`, `blocked_at` | уникальный индекс по `email` (в нижнем регистре) |
| `City` | `cities` | `name`, `is_active` | уникальный индекс по `name` |
| `Category` | `categories` | `name`, `parent_id`, `is_active`, `sort_order` | самоссылка `parent_id → categories.id`, `sort_order ≥ 0` |
| `Ad` | `ads` | `author_id`, `category_id`, `city_id`, `title`, `description`, `price`, `contacts`, `status`, `moderation_reason`, `published_at`, `reminder_sent_at` | `price >= 0`, `status` из списка |
| `AdPhoto` | `ad_photos` | `ad_id`, `file_name`, `thumbnail_file_name`, `content_type`, `byte_size`, `sort_order`, `width`, `height` | `sort_order BETWEEN 1 AND 5`, уникальность `(ad_id, sort_order)` |
| `AdComplaint` | `ad_complaints` | `ad_id`, `author_id`, `reason`, `status`, `closed_at`, `closed_by_user_id` | уникальность `(ad_id, author_id)`, `status` из списка |
| `UserToken` | `user_tokens` | `user_id`, `token_hash`, `purpose`, `expires_at`, `used_at` | уникальный индекс по `token_hash`, `purpose` из списка |

Перечисления (хранятся строками, имена — английские по требованию `platform` о языке артефактов):

- `UserRole`: `User`, `Moderator`, `Admin` (совпадает с `UserRole` из архивного `seed-demo-users`).
- `AdStatus`: `OnModeration`, `Active`, `Sold`, `Archived`, `Rejected`, `Hidden` — шесть статусов из `classified-ads`, `notifications`, `ad-search`.
- `ComplaintStatus`: `Open`, `Closed` (в интерфейсе — «закрыта»).
- `TokenPurpose`: `EmailConfirmation`, `PasswordReset`.

Смысловые решения по полям:

- `price` — `numeric(12,2)`, не `double`: цена в рублях должна быть точной; `CHECK (price >= 0)` переносит правило «неотрицательное число» в схему.
- `published_at` — начало текущего срока публикации, а не дата создания: от него считаются и автоархив (7 дней), и напоминание (за сутки), и продление, которое «отсчитывает срок заново». Отдельного `expires_at` нет, чтобы значение нельзя было рассинхронизировать; выборка фоновой задачи — `published_at <= now() - interval '7 days'`.
- `reminder_sent_at` сбрасывается в `NULL` при продлении — так «одно напоминание на срок» выражено одним полем без таблицы отправленных писем.
- `is_trusted` и `approved_ads_count` хранятся оба: доверие нельзя выводить из счётчика (`approved_ads_count >= 3`), потому что модератор выдаёт и отзывает доверие вручную, а отклонение объявления счётчик не сбрасывает (`ad-moderation`).
- `blocked_at` (nullable) вместо `is_blocked` + даты: одна колонка — одно состояние, нет противоречия «флаг стоит, даты нет». Значение = пользователь заблокирован.
- `moderation_reason` — одна колонка на отклонение и скрытие: объявление не может быть одновременно отклонено и скрыто, статус говорит, к какому решению относится причина. Автор видит причину рядом со статусом (`notifications`).
- `token_hash` — SHA-256 от токена из письма, а не сам токен: утечка дампа не даёт рабочих ссылок сброса. Ссылка одноразовая через `used_at`, просроченная — через `expires_at`.
- Идентификаторы — `uuid`, генерируются в приложении (`Guid.CreateVersion7()`), а не identity-колонкой: объект получает идентификатор до сохранения (нужно для путей медиа `/media/photos/<ad_id>/...`), значения не перебираются в URL, а UUIDv7 сохраняет порядок вставки и локальность индекса.

### 2. Ограничения в схеме и в коде

Требования, которые PostgreSQL не проверяет без триггеров, остаются правилами предметной области и покрываются тестами:

- Глубина дерева категорий ≤ 2 уровней и привязка объявления только к подразделу — проверка в сущности `Category` и в сценарии подачи; схема самоссылкой это не ловит.
- Запрет жалобы на своё объявление — сравнение `author_id` жалобы и объявления в сценарии.
- Пять фотографий на объявление — в схеме через `sort_order` 1..5 и уникальность `(ad_id, sort_order)`; это даёт максимум пять строк на объявление без счётчиков.

Альтернатива «отдельные таблицы `sections` и `subsections`» сделала бы оба ограничения категорий структурными, но удвоила бы администрирование, упорядочивание и сборку публичного дерева. Выбрана одна таблица: дерево всё равно отдаётся как дерево, а глубина — одно правило с тестом.

### 3. Соглашения схемы

- Имена таблиц и столбцов — по соглашению `UseSnakeCaseNamingConvention` (уже подключено), без ручных `ToTable`/`HasColumnName`; имена таблиц задаются множественными именами наборов (`Users` → `users`).
- Связи настраиваются явно в `IEntityTypeConfiguration<T>` (по файлу на сущность в `Persistence/Configurations`), а не соглашениями: поведение удаления должно быть осознанным.
- Удаление: `ads → ad_photos` и `ads → ad_complaints` — каскад (удалённое автором объявление не оставляет сирот); `ads.category_id`, `ads.city_id` — `Restrict`, потому что категории и города не удаляются при наличии объявлений, а деактивируются (`categories`, `locations`); `ads.author_id` — `Restrict`, удаление пользователей не предусмотрено.
- Перечисления — `varchar` + `CHECK`, а не нативный тип PostgreSQL: значения видны в дампе, добавить статус можно миграцией без `ALTER TYPE`. Целое число отклонено — нечитаемо в базе.
- `created_at`/`updated_at` — `timestamptz` (UTC), заполняются переопределением `SaveChanges` через `TimeProvider`. Триггеры на `updated_at` отклонены: поведение становится невидимым и нетестируемым на уровне модели.
- Индексы под сценарии: `ads (status, published_at desc)` — лента и автоархив; `ads (category_id, status)`, `ads (city_id)`, `ads (author_id, created_at)` — фильтры, «мои объявления» и суточный лимит; `ad_complaints (status, created_at)` — очередь жалоб; `user_tokens (user_id, purpose)`.
- Поиск по подстроке (`ad-search`: регистронезависимая подстрока в заголовке и описании) — `ILIKE '%...%'`, обычный индекс не помогает. `pg_trgm`/GIN и `tsvector` отклонены сейчас: первый требует расширения в миграции, второй меняет семантику на поиск по словам. Возвращаться к индексу — когда данных станет много.

### 4. Применение миграций

- Миграция создаётся командой `dotnet ef migrations add InitialSchema` из локального манифеста (`dotnet new tool-manifest` + `dotnet tool install dotnet-ef`), проект — `Doska.Infrastructure`, запуск — `Doska.Api`, каталог — `backend/src/Doska.Infrastructure/Migrations`.
- `AppDbContextFactory : IDesignTimeDbContextFactory<AppDbContext>` в `Doska.Infrastructure` даёт строку подключения инструментам времени разработки. Иначе `dotnet ef` поднимает хост `Doska.Api` и выполняет стартовый код, включая применение миграций, — то есть инструмент миграций воевал бы сам с собой.
- Применение при старте — в `Program.cs` до `MapControllers()`: получить scope, вызвать `Database.Migrate()`. Ошибка миграции валит запуск, и новая версия не начинает обслуживать запросы — это и есть требование `platform`. Идемпотентность обеспечивает EF: применяются только неприменённые миграции.
- Применение на старте управляется настройкой `Database:MigrateOnStartup` (по умолчанию `true`). Причина — существующие тесты API (`WebApplicationFactory<Program>`) не имеют базы и не должны требовать PostgreSQL; в `ApiFactory` настройка выключается. Отдельно нигде не включается: на реальном стенде значение по умолчанию и есть требуемое поведение. Альтернатива «применять только в `Production`» отклонена — тогда локальный запуск не проверяет миграции.

## Risks / Trade-offs

- Глубину категорий и запрет жалобы на своё объявление проверяет только код → ошибка в сценарии создаст некорректные данные. Митигация: тесты модели и сценариев, запись в базу только через API (ручная правка схемы и данных запрещена требованием `platform`).
- `Database.Migrate()` на старте делает PostgreSQL обязательной для запуска API: без базы приложение не поднимется, даже чтобы ответить `/api/health`. Это цена требования «миграции до обработки запросов»; смягчение — `Database:MigrateOnStartup=false` для тестов и для сценариев, где база поднимается отдельно.
- `Database.Migrate()` небезопасен при одновременном старте нескольких экземпляров: EF берёт блокировку таблицы истории миграций, но параллельные миграции в первой версии не поддерживаются. Митигация: один экземпляр API на стенде; при масштабировании — отдельный шаг применения до старта.
- Параллельные одобрения модераторов могут увеличить `approved_ads_count` дважды (нет токена конкурентности). В первой версии не решается; при реализации модерации добавить `xmin` как `IsRowVersion` или условное обновление.
- Суточный лимит подачи считается по строкам `ads`, поэтому удаление объявления освобождает квоту. Поведение не задано спецификацией; решение отложено до сценария подачи (см. открытые вопросы), схема допускает и мягкое удаление отдельной миграцией.
- Длины строк (`title` 200, `contacts` 500, `description` и причина — `text`) выбраны нами, спецификации их не задают; несовпадение с будущими формами исправляется миграцией, но лучше подтвердить до реализации.
- Составной `CHECK` на статусы нужно поддерживать в согласии с перечислениями: добавление значения в `enum` без миграции упадёт на ограничении. Митигация: тест, сверяющий значения `CHECK` и перечисления.

## Migration Plan

1. `dotnet new tool-manifest` в `backend`, установка `dotnet-ef` версии 10.x.
2. Сущности в `Doska.Domain`, конфигурации и `AppDbContext` в `Doska.Infrastructure`, фабрика времени разработки.
3. `dotnet ef migrations add InitialSchema` → `Migrations/<timestamp>_InitialSchema.cs` + `AppDbContextModelSnapshot.cs`. Миграция коммитится вместе с кодом, ручные правки в неё не вносятся.
4. `dotnet ef database update` против базы из `docker compose` (порт 5433) — проверка на чистой базе.
5. Запуск API: миграции применяются на старте; повторный запуск ничего не применяет; остановленная база не даёт приложению стартовать.
6. Откат: `dotnet ef database update <предыдущая миграция>`; для первой миграции — удаление схемы (`DROP SCHEMA public CASCADE; CREATE SCHEMA public;`) на локальном стенде. Продакшн-откат — возврат предыдущей версии приложения, схема при этом остаётся совместимой.

## Open Questions

- Считать ли удалённое объявление израсходованной квотой суточного лимита. Решается вместе со сценарием подачи; если «да» — вместо физического удаления понадобится мягкое (`deleted_at`), это отдельная миграция.
- Нужна ли отдельная таблица настроек площадки: `user-accounts` упоминает «настройки площадки» в правах администратора, но требований к ним нет. Появится вместе с требованиями.
- Сортировка городов: `locations` требует только добавление, переименование и деактивацию, порядок не задан. Если понадобится ручной порядок — добавим `sort_order` миграцией.
