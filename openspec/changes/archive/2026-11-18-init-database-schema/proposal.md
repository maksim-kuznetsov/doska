# Proposal

## Why

Спецификации описывают объявления, категории, города, жалобы, роли и доверие, но хранить эти данные негде: `AppDbContext` пуст, в базе нет ни одной таблицы, миграций нет. Ни одну возможность площадки нельзя реализовать, пока сущности и схема не описаны. Заодно закрывается отложенный пункт `platform` «Применение миграций»: сейчас API стартует, не применяя миграции, и первая миграция — первый случай, когда это требование становится проверяемым.

## What Changes

- **Сущности предметной области** в `Doska.Domain` — по спецификациям: пользователь, город, категория (раздел и подраздел в одной таблице), объявление, фотография объявления, жалоба, одноразовый токен (подтверждение email, сброс пароля).
- **Конфигурация модели** в `Doska.Infrastructure` — `AppDbContext` с наборами сущностей и отдельными конфигурациями `IEntityTypeConfiguration<T>`: связи и их кардинальность, обязательность полей, длины строк, уникальные индексы, ограничения значений, перечисления хранятся строками.
- **Первая миграция** `InitialSchema` для PostgreSQL и применение миграций при старте API до обработки запросов (`Database.Migrate()`), как требует требование `platform` «Применение миграций».
- **Типы данных под сценарии**: цена — `numeric` с неотрицательным ограничением, моменты времени — `timestamptz` (UTC), причина отклонения и скрытия — отдельное поле объявления, счётчик одобрений и признак доверия — поля пользователя, отметка об отправленном напоминании — поле объявления.
- **Каскады и удаление**: удаление объявления автором уносит его фотографии и жалобы; города и категории не удаляются физически при наличии объявлений, а деактивируются.
- **BREAKING**: нет, схема создаётся с нуля; существующие данные не переносятся.

## Capabilities

### New Capabilities

Нет: изменение не вводит новой возможности системы, а создаёт хранилище для уже описанных.

### Modified Capabilities

Нет. Схема базы данных и применение миграций уже описаны требованиями `platform` («Доступ к данным через EF Core и PostgreSQL»); наблюдаемое поведение площадки не меняется, меняется только его реализация. Поэтому change объявлен с `skip_specs: true`, спецификации не затрагиваются.

## Impact

- `backend/src/Doska.Domain` — новые сущности и перечисления, без ссылок на другие проекты решения.
- `backend/src/Doska.Infrastructure/Persistence` — `AppDbContext`, конфигурации сущностей; `Migrations/` — миграция `InitialSchema` вместе со снимком модели.
- `backend/src/Doska.Api` — применение миграций при старте до `MapControllers()`, фабрика контекста для команд `dotnet ef` (время разработки).
- `backend/tests/Doska.Tests` — проверки модели (связи, индексы, имена таблиц и столбцов в snake_case) и применения миграций на пустой базе.
- Инструменты и окружение: локальный манифест с `dotnet-ef`; PostgreSQL из `docker compose` на порту хоста 5433; проверка запускается из `backend`.
- Риски: применение миграций на старте делает базу обязательной для запуска API; ошибка миграции останавливает запуск, и релиз не переключается на новую версию — это и есть требуемое поведение, но локальный запуск без PostgreSQL теперь падает, а не деградирует.

## Вне рамок

- Эндпоинты, сценарии использования, DTO и ответы API — тела запросов и ответов по требованию `platform` не переиспользуют сущности, поэтому контракты появятся вместе с эндпоинтами.
- Начальные данные: справочник городов, дерево категорий, демо-аккаунты — отдельные изменения (наполнение, а не схема).
- Бизнес-правила поверх полей (суточный лимит, автоархив, повышение доверия, письма) — здесь только данные, на которых они будут считаться.
- Хранение медиафайлов: в базе только метаданные фотографии, сами файлы — через существующую абстракцию хранилища.
- Полный `docker compose` (api + frontend/nginx) и продакшн-развёртывание.
