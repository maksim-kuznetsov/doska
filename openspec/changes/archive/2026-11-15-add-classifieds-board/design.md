# Design

## Context

Проект создаётся с нуля: в репозитории нет кода, только каталог `openspec/`. Требования описаны в `proposal.md` и дельта-спецификациях `specs/*/spec.md`.

Ограничения, задающие архитектуру:

- Один VPS с диском 10 ГБ и небольшим объёмом RAM; отдельного объектного хранилища нет.
- Один разработчик, первая версия должна быть простой в развёртывании и поддержке.
- Публичная доска: ставка на модерацию и антиспам, а не на мгновенную масштабируемость.
- Фотографии занимают основное место на диске, их объём нужно держать под контролем.

## Goals / Non-Goals

**Goals:**

- Монорепозиторий: SPA на Vue 3 и Web API на ASP.NET Core.
- Прозрачная схема статусов объявления и доверия автора, проверяемая тестами.
- Управление справочниками и пользователями через административные эндпоинты Web API (`/api/admin/...`) и экраны `web/src/views/admin/`, модерация — через представления `web/src/views/moderation/`.
- Развёртывание одним `docker compose up` на VPS, бэкапы БД и медиа за пределами сервера.

**Non-Goals:**

- Горизонтальное масштабирование, кэш-кластеры, очереди задач и Redis в первой версии.
- Мобильное приложение и GraphQL: REST API — часть целевой архитектуры, отдельный GraphQL-слой и мобильный клиент не делаем.
- Полнотекстовый поиск с морфологией и ранжированием.
- Переезд на S3 в рамках этой поставки — только совместимость настроек.

## Decisions

### 1. SPA на Vue 3 поверх Web API на ASP.NET Core

Приложение — SPA на Vue 3 (Composition API, TypeScript, Vite, Pinia) и Web API на ASP.NET Core. Интерактивность вроде загрузки фото и фильтров реализуется компонентами SPA, обращающимися к эндпоинтам API; фильтры передаются query-параметрами `GET /api/ads`.

**Почему:** единый контракт API, интерактивность без перезагрузки страниц, один клиентский стек. **Альтернативы:** Razor Pages с серверным рендерингом (меньше JS, но нет единого SPA), Next.js + API (другой рантайм на клиенте и сервере).

### 2. Разделение на проекты решения по возможностям

```
+------------------------------------------------------------+
| Doska.sln (src/Doska.Api — Program.cs, контроллеры)        |
+------------------------------------------------------------+
|  src/Doska.Domain — сущности, роли, доверие, статусы       |
|  src/Doska.Application — сценарии, DTO, валидация          |
|  src/Doska.Infrastructure — EF Core, миграции, почта, файлы |
|  src/Doska.Api — контроллеры:                             |
|    AccountController, AdsController,                       |
|    CategoriesController, CitiesController,                 |
|    ModerationController, ComplaintsController,             |
|    SearchController, Notifications                         |
+------------------------------------------------------------+
```

`Doska.Domain` владеет сущностью `User` и правилами ролей; сценарии `Doska.Application` вызывают сервисы смены статусов объявлений. Зависимости направлены от модерации и поиска к объявлениям и пользователям, обратных зависимостей нет.

**Почему:** границы совпадают с capability-спецификациями, проще тестировать и позже выносить. **Альтернатива:** один проект без разделения — быстрее начать, но хуже сопровождается.

### 3. Модель данных

```
User (вход по email, роль полем UserRole)
  Role: User | Moderator | Admin
  IsBlocked, EmailVerifiedAt
  IsTrusted, ApprovedAdsCount
  TrustChangedBy, TrustChangedAt

Category
  Parent FK -> Category (null = раздел), Name, Slug, IsActive, SortOrder
  ограничение: Parent.Parent IS NULL (не глубже 2 уровней)

City
  Name, Slug, IsActive, SortOrder

Ad
  Author FK -> User
  Category FK -> Category (только подраздел)
  City FK -> City
  Title, Description, Price (>= 0), Contacts
  Status: Pending | Active | Sold | Rejected | Hidden | Archived
  PublishedAt, ExpiresAt
  ModerationReason, ModeratedBy, ModeratedAt

AdPhoto
  Ad FK, Image, Thumbnail, SortOrder

Complaint
  Ad FK, Reporter FK, Reason, Status: Open | Closed
  ResolvedBy, ResolvedAt, ResolutionNote

ModerationAction (аудит)
  Moderator FK, Ad FK, Action, Reason, CreatedAt
```

Инварианты:

- `ExpiresAt` заполняется только при переходе в `Active` и равен моменту публикации + 7 дней.
- `Status = Pending` не имеет `PublishedAt`/`ExpiresAt`.
- Фотографии удалённого объявления удаляются с диска каскадно.
- Пара `(Ad, Reporter)` в жалобах уникальна.

**Почему:** явные статусы и аудит упрощают модерацию и разбор спорных решений. **Альтернатива:** хранить историю статусов отдельной таблицей — избыточно для v1, аудит решений покрывает потребность.

### 4. Роли — одно поле вместо групп и разрешений

`User.Role` — перечисление `UserRole` с тремя значениями, плюс свойства `IsModerator`, `IsAdmin` и атрибуты авторизации на контроллерах. Группы и разрешения платформы не используются.

**Почему:** роли фиксированы и не настраиваются, одна роль на пользователя; поле проще проверять и отображать. **Альтернатива:** группы и наборы разрешений — гибче, но добавляет косвенность без реальной потребности.

### 5. Модерация: экраны SPA, справочники — через административные эндпоинты

Очередь проверки, карточка решения, очередь жалоб и «Мои объявления» — представления `web/src/views/moderation/` поверх API с понятным модератору интерфейсом. Административные эндпоинты `/api/admin/...` и экраны `web/src/views/admin/` используются для категорий, городов, пользователей, ролей и настроек администратором.

**Почему:** модерация — ежедневный сценарий, ради которого стоит сделать удобный экран; справочники меняются редко и отлично живут в административных эндпоинтах. **Альтернатива:** всё через административные эндпоинты — быстрее, но отклонение с причиной и очередь жалоб там неудобны; всё своё — лишняя работа.

### 6. Переходы статусов через сервисный слой

Смена статусов выполняется сервисами `src/Doska.Application` (`SubmitAd`, `ApproveAd`, `RejectAd`, `HideAd`, `MarkSold`, `Relist`, `Renew`, `ArchiveExpired`) с проверкой допустимости перехода, записью `ModerationAction` и постановкой письма.

**Почему:** правила жизненного цикла не расползаются по контроллерам и DTO, их легко покрыть тестами. **Альтернатива:** интерцепторы EF Core — неявны и плохо тестируются.

Схема переходов статусов:

```
            +-----------+
 submit --> |  pending  | --approve--> +--------+ --7 дней--> +---------+
            +-----------+              | active |              | archived|
                 |                     +--------+              +---------+
                 | reject                 |    ^                     ^
                 v                        |    | renew               |
            +-----------+                 |    +---------------------+
            | rejected  |                 | mark_sold
            +-----------+                 v
                                   +--------+  relist  +--------+
                                   |  sold  | -------> | active |
                                   +--------+          +--------+
            active --hide--> +--------+
                             | hidden |
                             +--------+
```

### 7. Срок жизни и фоновые задачи — фоновая служба в приложении

Автоархив и напоминания реализуются идемпотентными службами `ArchiveExpiredService` и `SendExpiryRemindersService` (`BackgroundService` в `src/Doska.Api`). На VPS запуск выполняется по расписанию раз в час.

**Почему:** отсутствие брокера сообщений экономит RAM и упрощает деплой; при объёмах доски часовой задержки архивации достаточно. **Альтернатива:** отдельный планировщик с очередью — оправдан позже, когда появятся тяжёлые задачи (например, обработка видео).

Идемпотентность: архивация выбирает `Active` с `ExpiresAt <= now`; напоминание фиксируется полем `ExpiryReminderSentAt` в объявлении и сбрасывается при продлении.

### 8. Фотографии: локальный диск, сжатие, отдача через nginx

Загрузка идёт через Web API, ImageSharp уменьшает изображение до разумного размера (например, длинная сторона 1600 px) и создаёт миниатюру. Файлы хранятся в каталоге `media/` с UUID-именами, nginx отдаёт их напрямую по `/media/...`.

**Почему:** нет внешнего хранилища, nginx отдаёт статику эффективнее приложения. **Альтернатива:** `X-Accel-Redirect` через эндпоинт API — строже проверяет статус объявления, но добавляет нагрузку; UUID-имена делают перебор URL нецелесообразным. Переезд на S3 — смена реализации `IFileStorage`, сущности не меняются.

Лимиты: не более 5 фото на объявление, не более 5 МБ на файл, принимаются JPEG/PNG/WebP.

### 9. Поиск: `ILIKE` + trigram-индексы

Лента фильтруется query-параметрами `GET /api/ads` по подразделу (или разделу с поддеревом), городу, диапазону цены, поиск — `EF.Functions.ILike` по заголовку и описанию. Индексы `pg_trgm` GIN ускоряют подстрочный поиск; сортировка по `PublishedAt` или `Price`, пагинация по 20.

**Почему:** пользователи ждут подстрочное совпадение, а не морфологию; до тысяч объявлений это быстро. **Альтернатива:** `tsvector` с конфигурацией `russian` — лучше для больших объёмов, вводится позже без изменения контракта фильтров.

### 10. Аутентификация и защита

Email — логин. Подтверждение email и сброс пароля — письма с одноразовыми токенами. Пароли — штатный хешер ASP.NET Core. Защита: antiforgery-токен для изменяющих запросов, cookie-сессия (`httpOnly`, `SameSite=Lax`), HTTPS и HSTS за nginx, ограничение частоты запросов middleware ASP.NET Core (RateLimiter) на вход, регистрацию, сброс пароля и подачу объявлений, проверка блокировки в middleware.

**Почему:** штатные механизмы платформы аудированы и не требуют своих криптоконструкций. **Альтернатива:** внешний провайдер идентификации — больше возможностей (OAuth), но для v1 избыточен; OAuth добавим отдельным изменением.

### 11. Почта через Resend по SMTP

SMTP-клиент приложения указывает на `smtp.resend.com` с API-ключом из окружения. Письма отправляются синхронно после фиксации транзакции, ошибки логируются и не откатывают решение модератора.

**Почему:** минимум зависимостей, не нужен SDK. **Альтернатива:** HTTP API Resend — быстрее при массовых рассылках, для v1 не требуется. На домене настраиваются SPF и DKIM.

### 12. Развёртывание: Docker Compose на одном VPS

```
+--------------------------------------------------------+
| VPS (10 ГБ диск)                                       |
|  +-----------+   +-------------+   +----------+        |
|  |  web      |-->| api         |-->| postgres |        |
|  | nginx+SPA |   | ASP.NET Core |   |          |        |
|  | :80/:443  |   +------+------+   +----------+        |
|  +-----+-----+          |                              |
|        |         +------v------+                       |
|        +-------->| media/      |  volume               |
|                  +-------------+                       |
|  фоновая служба api --> автоархив и письма             |
+--------------------------------------------------------+
              | ночной бэкап (dump + restic)
              v
        внешнее хранилище (B2/R2)
```

- Сервисы: `api` (ASP.NET Core), `web` (nginx и собранный SPA), `postgres`, volume для БД и медиа.
- Миграции — отдельным шагом деплоя до перезапуска `api`; сборка SPA (`pnpm build` в каталоге `web`) в образ.
- Секреты — `.env`, не в git; `ASPNETCORE_ENVIRONMENT=Production` из окружения.
- Бэкапы: ежедневный `pg_dump` и инкрементальный бэкап медиа во внешнее хранилище; проверка восстановления раз в месяц.

## Risks / Trade-offs

- **Диск 10 ГБ может заполниться фото** → сжатие при загрузке, лимит 5 фото и 5 МБ, мониторинг свободного места, алерт при 80% заполнения.
- **Один VPS — единая точка отказа** → ежедневные бэкапы БД и медиа во внешнее хранилище, документированная процедура восстановления, возможность быстро поднять новый сервер из compose-файла.
- **Прямая отдача фото через nginx раскрывает URL скрытого объявления** → UUID-имена файлов; при необходимости перейти на `X-Accel-Redirect` с проверкой статуса.
- **Синхронная отправка писем замедляет запрос** → отправка после фиксации транзакции, таймаут SMTP, логирование ошибок без отката решения.
- **Фоновая служба может не сработать незаметно** → задачи идемпотентны, логируют результат, добавлен health-check/алерт по последнему запуску.
- **`ILIKE` деградирует на больших объёмах** → trigram-индексы и переход на `tsvector` при росте; контракт фильтров не меняется.
- **Автоповышение доверия после 3 одобрений можно накрутить** → ручной отзыв доверия модератором, аудит решений, лимит 5 объявлений в сутки.
- **Письма попадают в спам** → свой домен, SPF/DKIM, Resend как проверенный отправитель.

## Migration Plan

1. Развернуть пустую БД, применить миграции EF Core (`dotnet ef database update`), создать администратора через seed-сервис.
2. Загрузить стартовые категории и города seed-сервисом (`dotnet run --project src/Doska.Api -- seed`).
3. Настроить домен, TLS (certbot), SPF/DKIM для Resend.
4. Включить фоновые задачи и ночные бэкапы, проверить восстановление на тестовой БД.
5. Деплой новых версий: бэкап → миграции → перезапуск `api`; откат — предыдущий образ и восстановление БД из дампа.
