# Proposal

## Why

Разбор числовых полей формы в API зависит от культуры потока сервера: значение типа `decimal` в `multipart/form-data` (`CreateAdForm.Price`) привязывается через `CultureInfo.CurrentCulture` (`FormValueProviderFactory`). На хосте или контейнере с локалью `ru-RU` значение в инвариантном формате с точкой (`10000000000.99`) не разбирается, поэтому `[ApiController]` возвращает обобщённый `400 ValidationProblemDetails` раньше, чем вызывается `AdService.ValidateCommand`. Из-за этого на ru-RU падает тест `ClassifiedAdsApiTests.Create_rejects_price_above_database_range` (проверено: `ru-RU` не разбирает ни `10000000000.99`, ни `9999999999.99`), и та же зависимость делает поведение подачи объявления непредсказуемым на сервере с «русской» локалью. Query-параметры и тело JSON разбираются инвариантно уже сейчас (`QueryStringValueProviderFactory` и `System.Text.Json`), поэтому зависимость проявляется только на форме подачи. В CI (en-US/инвариант) дефект скрыт.

## What Changes

- Сделать разбор чисел в `multipart/form-data` культуронезависимым: числовые поля (например, `decimal`) разбираются в инвариантной культуре независимо от локали сервера; query-параметры и JSON уже инвариантны.
- Поведение и контракт не меняются: коды ответов и тексты сообщений те же, включая `400` с сообщением «Цена не должна превышать 9 999 999 999,99 ₽.»; успешная подача по-прежнему `201 Created`.
- Добавить регрессионные тесты, которые ловят зависимость разбора от культуры, в том числе на хосте с запятой-разделителем.
- **BREAKING**: нет.

## Capabilities

### New Capabilities

Нет: изменение уточняет существующее техническое требование к контракту Web API.

### Modified Capabilities

- `platform`: capability дополняется новым требованием о культуронезависимом разборе числовых полей запроса, не зависящем от локали сервера.

## Impact

- Код: `backend/src/Doska.Api/Program.cs` (конфигурация культуры разбора запросов).
- Тесты: `backend/tests/Doska.Tests` (регрессионные проверки разбора цены и фильтров).
- Контракт API, схема базы данных и миграции не меняются; интерфейс (`frontend/`) не затрагивается.

## Вне рамок

- Изменения во фронтенде: клиент уже передаёт числа в инвариантной (POSIX) записи, потому что поле цены — `input[type=number]`, поиск использует `Number.parseFloat`/`String`, редактирование — `JSON`. Зависимости от локали браузера нет (см. `design.md`, решение 3).
- Необязательное улучшение UX: нормализация и валидация пользовательского ввода цены во фронтенде (приём и запятой, и точки, разделители групп) — возможное отдельное изменение, не требующееся для этого бага.
- Изменение бизнес-лимитов цены и текстов сообщений об ошибке.
- Локализация ответов API по `Accept-Language`: сервер отдаёт тексты на русском языке независимо от запроса.
