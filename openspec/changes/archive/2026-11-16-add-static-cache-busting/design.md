# Design

## Context

Сейчас `pnpm build` в каталоге web собирает ассеты без версионирования имён, поэтому адреса в HTML-оболочке SPA всегда одинаковые. `deploy/nginx.conf` и `deploy/nginx.https.conf` отдают ассеты из `web/dist/` с `expires 7d`; HTTPS-конфиг на сервере копируется поверх основного (`cp deploy/nginx.https.conf deploy/nginx.conf`), поэтому правки нужны в обоих файлах. При сборке образа `web` выполняется `pnpm build`, собранные ассеты попадают в `web/dist/`, nginx читает их оттуда.

Тесты запускаются без предварительной сборки, а окружение Vitest не требует собранного манифеста. Для локальной разработки запускается dev-сервер Vite, который отдаёт модули без сборки.

## Goals / Non-Goals

**Goals:**

- Автоматическая версия в адресах CSS и JS без ручного бампа номера версии.
- Свежий HTML после деплоя при сохранении браузерного кеша статики.
- Тесты и локальный запуск не требуют `pnpm build`.
- Изменение одинаково работает и в HTTP-, и в HTTPS-конфиге nginx.

**Non-Goals:**

- Не увеличиваем срок кеширования ассетов и не добавляем CDN.
- Не версионируем медиа: у фото UUID-имена.
- Не меняем формат доставки кода (`sync.ps1`/`release.sh`), кроме перезагрузки nginx для применения конфига.

## Decisions

### 1. Хеш содержимого в именах файлов вместо `?v=`

Выбран встроенный механизм Vite: `pnpm build` создаёт файлы с хешем содержимого (`base.<hash>.css`) и манифест `web/dist/.vite/manifest.json`, а Vue-компоненты получают имя из манифеста. Версия меняется сама при изменении файла, разметка остаётся нетронутой, а nginx продолжает отдавать обычные файлы — без обработки query-строк и без правки HTML вручную.

Альтернативы:

- `?v=<версия>` из настройки: требует ручного обновления версии при каждом деплое, иначе кеш снова устаревает.
- Собственный расчёт хеша на клиенте: больше кода и I/O при каждом запросе; манифест Vite делает то же штатными средствами.

В окружении Development dev-сервер Vite отдаёт модули без хеша, поэтому локальный запуск и страница-гайд работают без собранного манифеста.

### 2. Тесты не требуют собранных ассетов

Vitest запускается без предварительного `pnpm build`, поэтому тесты не зависят от манифеста и работают с компонентами напрямую. Это меняет только тестовое окружение; продакшен-сборка проверяется отдельным тестом, который читает `web/dist/.vite/manifest.json` и убеждается, что имена ассетов содержат хеш.

Альтернатива — требовать `pnpm build` перед всем набором тестов: удлиняет прогон ради одной настройки, поэтому отклонена.

### 3. Кеширование HTML через `map` по Content-Type

В nginx добавляется:

```nginx
map $upstream_http_content_type $doska_html_cache_control {
    ~*^text/html "no-cache";
    default       "";
}
```

и в `location /` — `add_header Cache-Control $doska_html_cache_control always;`. Для не-HTML ответов значение пустое, и nginx заголовок не добавляет (пустое значение `add_header` не отправляется). Заголовок работает и для ответов 4xx/5xx (`always`).

Альтернатива — безусловный `add_header` в `location /`: проще, но вешает `no-cache` на редиректы и любые не-HTML ответы Web API; выбран точный вариант.

Если Web API уже отдал `Cache-Control` (например, для запрета кеширования на страницах входа), nginx добавит второй заголовок. Дублирование допустимо: по HTTP несколько значений объединяются, и `no-cache` в списке сохраняется. `proxy_hide_header Cache-Control` не используем, чтобы не терять `private`/`no-store` от API.

### 4. Перезагрузка nginx при выпуске и откате

`docker compose up -d --build` не пересоздаёт nginx, если изменился только файл конфига в bind mount: контейнер продолжит работать со старым конфигом. Поэтому `deploy/release.sh` и `deploy/rollback.sh` после `up -d --build` выполняют `docker compose exec -T nginx nginx -s reload`. Это дешевле рестарта и не рвёт соединения.

## Risks / Trade-offs

- [Ссылка на несуществующий ассет] → Vite не положит его в манифест, и загрузка страницы завершится ошибкой. Риск низкий: все текущие файлы на месте, а тест с `pnpm build` ловит такие опечатки до деплоя.
- [Устаревший `web/dist/.vite/manifest.json`] → манифест пересоздаётся при каждой сборке образа `web`, поэтому nginx читает актуальный файл. Старые хешированные файлы в `web/dist/` остаются и не мешают; каталог не очищаем полностью, чтобы не удалять файлы, на которые ещё могут ссылаться открытые страницы.
- [Смешанные версии при откате] → `rollback.sh` восстанавливает код и пересобирает ассеты, старые файлы остаются в `web/dist/`; перезагрузка nginx возвращает и старый конфиг.
- [Дубли `Cache-Control` на страницах без кеширования] → оба значения требуют ревалидации; поведение не меняется.
- [Забыли перезагрузить nginx вручную при нестандартном деплое] → `DEPLOY.md` дополняется явной проверкой заголовка после обновления.

## Migration Plan

1. Выпустить код обычным `.\deploy\sync.ps1 -Target doska`: `pnpm build` и `dotnet publish` пересобирают приложение, Vite создаёт хешированные файлы и манифест, скрипт перезагружает nginx.
2. Проверить: `curl -sI https://домен/ | grep -i cache-control` даёт `no-cache`, а HTML-оболочка ссылается на `base.<hash>.css`.
3. Откат — `./deploy/rollback.sh` на сервере; он возвращает код, пересобирает ассеты и перезагружает nginx.
