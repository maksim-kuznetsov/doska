# Design

## Context

Seed-сервис (`src/Doska.Infrastructure`), запускаемый командой `dotnet run --project src/Doska.Api -- seed`, уже наполняет дерево категорий и города идемпотентно: записи ищутся по `slug`, существующие не перезаписываются. Он выполняется на старте проекта и упомянут в `deploy/DEPLOY.md` (шаг 5) как часть инициализации production. Сущность `User` использует вход по email, роль хранится в `UserRole` (`User`, `Moderator`, `Admin`), доступ к модерации даёт роль `Moderator`, к административным эндпоинтам `/api/admin/...` — роль `Admin`. См. `proposal.md` — Why.

## Goals / Non-Goals

**Goals:**

- Один запуск seed-сервиса даёт готовые аккаунты на все три роли с известными кредами.
- Повторный запуск безопасен: ничего не дублируется и не перезаписывается.
- Разработчик видит предупреждение об удалении демо-аккаунтов, а инструкция деплоя требует это сделать.

**Non-Goals:**

- Демо-объявления, фотографии, жалобы и другие тестовые данные.
- Отдельная команда или флаг для демо-аккаунтов: по решению пользователя они создаются всегда вместе со справочниками.
- Автоматическое удаление демо-аккаунтов на production: удаление остаётся ручным шагом с явно описанным вызовом.
- Ослабление серверных правил сложности пароля.

## Decisions

- **Три адреса на домене `example.com`**: `user@example.com`, `moderator@example.com`, `admin@example.com`. Домен зарезервирован для примеров, не пересекается с реальными ящиками и легко находится для удаления.
- **Общий пароль `123789`.** По решению пользователя — простой и одинаковый для всех. Пароль записывается в сущность `User` напрямую через хеширование, поэтому серверная проверка сложности (8 символов, не только цифры) не применяется; это осознанно и допустимо только для демо-аккаунтов.
- **Администратор получает роль `UserRole.Admin`**: этого достаточно для административных эндпоинтов `/api/admin/...` и экранов администрирования SPA (`web/src/views/admin/`). Модератор получает только роль `UserRole.Moderator` и работает через экраны модерации (`web/src/views/moderation/`) поверх API; доступ к административным эндпоинтам ему не выдаётся.
- **Все трое с заполненным `EmailVerifiedAt`**: без подтверждения нельзя подавать объявления и входить в часть сценариев, а демо-аккаунты должны работать сразу.
- **Идемпотентность через поиск существующего пользователя по email.** Если пользователь с таким адресом уже есть, он не изменяется: пароль и роль могли быть изменены вручную, и перезапись была бы неожиданной. Seed-сервис сообщает, сколько аккаунтов создано и сколько уже было.
- **Предупреждение печатается всегда, когда демо-аккаунты присутствуют в базе**, а не только при создании: повторный запуск на production тоже должен напомнить об удалении.
- **Удаление — документированный вызов с явным списком адресов**, оформленный как интеграционный тест (`tests/Doska.Tests`, xUnit + `WebApplicationFactory`) и запускаемый командой `dotnet test --filter RemoveDemoUsers`, а не автоматика и не отдельный флаг. Список из трёх адресов прозрачен при проверке и не может случайно задеть других пользователей.
- **Альтернатива «отдельный шаг сидирования демо-пользователей» отклонена** пользователем: нужен один шаг заполнения базы. Риск публично известных кредов на production закрывается обязательным шагом удаления в `DEPLOY.md`.

## Risks / Trade-offs

- [Демо-аккаунты попадут на production и дадут всем вход в модерацию] → seed-сервис печатает предупреждение, README и `DEPLOY.md` содержат обязательный шаг удаления сразу после его запуска; удаление — до открытия сайта.
- [Пароль `123789` не проходит серверные правила сложности] → аккаунты создаются seed-сервисом, форма регистрации не участвует; правила для реальных пользователей не меняются.
- [Кто-то уже зарегистрировал `user@example.com` вручную] → существующая запись не перезаписывается; seed-сервис сообщает, что аккаунт уже есть, и разработчик видит расхождение ролей при проверке.
- [Пароль известен из истории git даже после смены] → это демо-креды, они не должны использоваться на production; при утечке боевых данных проблема не в них, а в неудалённых демо-аккаунтах.
- [Существующие тесты наполнения справочников начнут падать из-за новых пользователей] → тесты проверяют категории и города, а не количество пользователей; новые проверки добавляются отдельно.

## Migration Plan

1. Изменения только в коде seed-сервиса, схема БД и миграции не меняются.
2. Локально: `dotnet run --project src/Doska.Api -- seed` — появляются три аккаунта, можно входить.
3. Production: после запуска seed-сервиса выполнить документированное удаление демо-аккаунтов, затем завести реального администратора с ролью `UserRole.Admin`.
4. Откат: вернуть предыдущий коммит и пересобрать; созданные демо-аккаунты удаляются тем же интеграционным тестом.
