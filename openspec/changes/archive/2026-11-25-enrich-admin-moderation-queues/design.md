# Design: Очереди модерации с полными данными объявления

## Context

См. proposal.md — Why. Текущее состояние, важное для решений:

- Очереди отдаются двумя эндпоинтами: `GET /api/moderation/queue` (`ModerationService.GetQueueAsync`) и `GET /api/complaints/queue` (`ComplaintService.GetQueueAsync`). Оба возвращают «плоские» записи без данных объявления.
- Полное объявление уже доступно модератору через `GET /api/ads/{id}` (`AdService.GetByIdAsync` с `canModerate`), DTO `AdResponse` содержит описание, цену, город, категорию, контакты и фотографии.
- Названия города и категории интерфейс получает отдельно из `/catalog` (`CatalogService`), а тот отдаёт только активные записи. В очереди модерации объявление может ссылаться на уже деактивированные город или категорию.
- Фотографии описываются `AdPhotoSummary` (имена файлов), а URL собирает `MediaUrls.Photo` в слое API.
- Контекст доверия хранится в `User`: `IsTrusted` и `ApprovedAdsCount`.
- Спецификация `design-system` требует, чтобы страницы собирались из компонентов системы, а страница-гайд показывала примеры всех компонентов; гайд уже содержит пример `ModerationQueueList`.

## Goals / Non-Goals

**Goals:**

- Одна запись очереди = один запрос; никаких N+1 обращений к API на карточку.
- Карточки обеих очередей содержат всё для решения: фотографии, цену, гео-категорию, описание, контакты, автора и контекст.
- Переиспользовать существующие представления и компоненты, не вводя новых бизнес-правил и миграций.

**Non-Goals:**

- Не добавляем переходы на отдельную страницу объявления (решение пользователя) и не меняем `AdDetailView`.
- Не меняем состав действий модератора и правила доверия.
- Не трогаем прочие админские страницы.

## Decisions

### 1. Расширять DTO очередей, а не догружать объявления по одному

Оба `QueueItem`-record'а расширяются полями объявления напрямую, ответ приходит одним запросом.
Альтернатива — оставить очереди краткими и запрашивать `GET /api/ads/{id}` на каждую карточку — отклонена: даёт N+1 запросов и мерцание карточек.

### 2. Названия города и категории — на сервере

В ответ добавляются `CityName` и `CategoryName`, вычисляемые при проекции через навигации `ad.City!` и `ad.Category!`.
Клиентское сопоставление по `/catalog` не подходит: каталог отдаёт только активные записи, а в очереди могут быть объявления с деактивированными городом или категорией.

### 3. Фотографии переиспользуют `AdPhotoSummary`, URL строит API

`Doska.Application` в записях очередей использует существующий `AdPhotoSummary` (имена файлов), а `ModerationContracts` преобразует их в URL через `MediaUrls.Photo` — так же, как `AdResponse`. Отдаются только URL, без бинарных данных.

### 4. Контекст автора и число жалоб — в слое Application

- Очередь проверки: `AuthorIsTrusted` (`User.IsTrusted`) и `AuthorApprovedAdsCount` (`User.ApprovedAdsCount`).
- Очередь жалоб: `AdAuthorEmail`, статус объявления и `OpenComplaintsCount` — число открытых жалоб на то же объявление (`AdComplaints.Count(c => c.AdId == complaint.AdId && c.Status == Open)`, транслируется EF в коррелированный подзапрос).

### 5. Общий компонент предпросмотра объявления в интерфейсе

Фото, цена, гео, описание и контакты нужны обеим очередям. Вводится презентационный компонент `AdminAdPreview.vue`, который используют `ModerationCard.vue` (расширяется) и новый `ComplaintCard.vue`. `ComplaintsQueueView.vue` переводится на `ComplaintCard`, чтобы не держать разметку карточки внутри представления (требование `design-system`).
Общий компонент и карточка жалоб показываются в примерах `DesignSystemGuide.vue`; существующий пример очереди проверки обновляется под новый тип записи.

### 6. Формат ответа и совместимость

Расширение DTO — добавление полей; потребитель — только собственный интерфейс, поэтому обратная совместимость не требуется. Схема БД не меняется, миграции не нужны.

## Risks / Trade-offs

- [Коррелированный подзапрос числа жалоб может быть дорогим на больших объёмах] → объём открытых жалоб в первой версии мал, индекс `ix_ad_complaints_status_created_at` покрывает фильтр по статусу; при росте можно вынести подсчёт в отдельный агрегат.
- [Рост размера ответа очереди за счёт полей объявления и URL фотографий] → передаются только URL и текст, без изображений; объём ограничен числом объявлений в очереди.
- [Раскрытие контактов автора в очереди] → доступ уже ограничен политикой `ModeratorOrAdmin`, и модератор и так видит контакты через `GET /api/ads/{id}`; нового доступа не появляется.
- [Расхождение гайда дизайн-системы с компонентами] → в задачи входит обновление `DesignSystemGuide.vue` и фикстуры очереди под новые поля.

## Migration Plan

Изменение приложения без изменения схемы: миграции не требуются. Выпуск обычный (`dotnet test`, `pnpm test`, пересборка `docker compose`); откат — возврат предыдущей версии, данные не затрагиваются.
