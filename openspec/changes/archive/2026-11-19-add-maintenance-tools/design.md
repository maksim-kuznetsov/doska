# Design

## Context

See `proposal.md` — Why. Текущее состояние:

- `LocalAdPhotoStorage` пишет оригинал и превью в `Media:RootPath/photos/<adId>/`; при удалении объявления файлы удаляются сценарием.
- `AdPhoto` хранит `FileName` и `ThumbnailFileName`; схема БД менять не нужно.
- Data Protection в Development использует эфемерное хранилище: после перезапуска API cookie-сессии и antiforgery-токены становятся недействительными.
- Сквозной сценарий проверяется вручную; интеграционные тесты покрывают отдельные эндпоинты, но не живой стенд.

## Goals / Non-Goals

**Goals:**

- Убрать осиротевшие файлы безопасной идемпотентной командой.
- Дать одну команду для сквозной проверки живого стенда.
- Сохранять dev-сессии между перезапусками.

**Non-Goals:**

- Фоновая периодическая очистка и S3.
- Браузерный e2e.
- Удаление демонстрационных данных.

## Decisions

### 1. Очистка медиа — сценарий с явной командой

`IMediaMaintenance.CleanupAsync` читает существующие `Ad.Id` и пары файлов из `ad_photos`, затем обходит каталоги `photos/*`:

- каталог с именем не-GUID или без объявления удаляется целиком;
- в каталоге существующего объявления удаляются файлы, которых нет среди `file_name`/`thumbnail_file_name` его фотографий;
- если после этого файлов не осталось, каталог удаляется.

Сценарий возвращает число удалённых каталогов и файлов. Запуск — CLI-команда `cleanup-media`; фоновая задача не добавляется, чтобы не выполнять разрушительные операции незаметно. Идемпотентность: повторный запуск ничего не находит.

### 2. Смоук — PowerShell и HttpClient

`scripts/smoke.ps1` использует `System.Net.Http.HttpClient` с CookieContainer: это надёжнее ручного разбора `curl` и работает в PowerShell 5.1. Скрипт:

1. проверяет `/api/health`;
2. регистрирует уникального пользователя и подтверждает email через `docker compose exec -T postgres psql` (иначе подача запрещена);
3. получает города и подразделы, создаёт объявление multipart с `scripts/fixtures/photo.png`;
4. проверяет статус «на проверке» и наличие фото;
5. входит модератором, находит объявление в очереди и одобряет;
6. проверяет появление в ленте по поисковой строке;
7. отмечает «Продано» и проверяет исчезновение из ленты;
8. удаляет объявление и пользователя.

Скрипт использует демо-модератора и не меняет доверие демо-пользователя. При ошибке — `throw` и ненулевой код возврата; очистка выполняется в `finally`.

### 3. Ключи Data Protection в Development

В Development ключи сохраняются в `media/keys` через `PersistKeysToFileSystem`. Это убирает эфемерное хранилище и сохраняет сессии при перезапуске API; каталог уже исключён из git как часть `media/`. В Production ключи лежат в именованном томе (change `harden-production-runtime`).

### 4. Тест очистки

Тест создаёт во временном каталоге валидный каталог объявления с привязанными файлами, лишний файл в нём и два осиротевших каталога; после очистки проверяет, что остались только привязанные файлы, а счётчики соответствуют удалённому. БД — реальная, временный каталог — в каталоге сборки тестов, чтобы не зависеть от `%TEMP%`.

## Risks / Trade-offs

- **Команда удаляет файлы безвозвратно** → запускается вручную; критерии строгие, невалидные каталоги и непривязанные файлы считаются мусором. Резервное копирование тома остаётся на администраторе.
- **Смоук зависит от `docker compose` и psql** → это локальный инструмент; параметры позволяют указать другой стенд, но подтверждение email требует доступа к БД.
- **Ключи Data Protection в `media/keys`** → dev-секреты лежат локально; каталог в git не попадает.

## Migration Plan

1. Добавить контракт и реализацию очистки, команду и тест.
2. Включить файловое хранилище ключей в Development.
3. Добавить смоук и фикстуру, описать в README.
4. Проверка: `dotnet build`, тесты, запуск смоука, перезапуск API с сохранением сессии.
5. Откат — удалить команду и скрипт; данные не затрагиваются.
