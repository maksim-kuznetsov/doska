# Design

## Context

Смотри `proposal.md` — Why. Текущее состояние, важное для решения:

- Вход и сессия уже построены на cookie-схеме ASP.NET Core (`doska.session`, `HttpOnly`, `SameSite=Lax`); на каждом запросе `OnValidatePrincipal` перечитывает пользователя из БД.
- Пароль обязателен на уровне схемы (`users.password_hash NOT NULL`), а `AuthService.LoginAsync` всегда проверяет хеш.
- Внешние провайдеры не подключены. API стоит за nginx/Caddy с forwarded headers, интерфейс в разработке ходит через Vite-прокси с `changeOrigin: true`.
- Публичный адрес сайта уже задаётся `App:PublicBaseUrl` и используется для ссылок в письмах.
- Миграции применяются автоматически при старте API; откат релиза возвращает предыдущую версию приложения без откатов схемы.

## Goals / Non-Goals

**Goals:**

- Google-вход и привязка без дублей аккаунтов, без хранения Google-токенов и без изменения модели cookie-сессии.
- Корректное поведение при откате релиза: старая версия API не должна падать на аккаунтах, созданных через Google.
- Изолированная, тестируемая логика разрешения Google-идентичности, независимая от сетевого обмена с Google.
- Секреты только в окружении; при отсутствии настроек приложение работает как раньше.

**Non-Goals:**

- Универсальный слой внешних провайдеров и таблица `user_external_logins` (провайдер один).
- Отвязка Google, смена email, слияние аккаунтов, импорт профиля Google.
- Проверка Google-идентичности в интеграционных тестах через реальную сеть.

## Decisions

### 1. Стандартный Google-хендлер, а не ручной OAuth

Используется пакет `Microsoft.AspNetCore.Authentication.Google` и `GoogleHandler`: он сам формирует challenge, проверяет `state`, обменивает код на токены, валидирует подпись/издателя id_token и получает userinfo.

Альтернативы: ручной OAuth с `HttpClient` и самостоятельной проверкой `id_token` — больше криптографического кода и риск ошибок; ASP.NET Core Identity — не используется в проекте и тянет лишнюю модель.

Хендлер подключается только при заполненных `Google:ClientId` и `Google:ClientSecret`. Обратный вызов — `/api/auth/google/callback`, временная cookie-схема `GoogleExternal` (короткий срок, не участвует в авторизации API) указана как `SignInScheme`. Вся бизнес-логика выполняется в `OnTicketReceived`, после чего вызывается `HandleResponse()` — это не даёт хендлеру выписать временную cookie и уводит браузер сразу на нужный адрес.

Correlation-cookie хендлера явно настраивается как `HttpOnly`, `SameSite=Lax`, `SecurePolicy=SameAsRequest`: обратный вызов Google — top-level GET, поэтому Lax достаточно, а значение по умолчанию `SameSite=None` не работает по HTTP в локальной разработке.

### 2. Google-идентичность хранится в `users`

В `User` добавляются nullable `GoogleSubject` (уникальный индекс) и `HasPassword`. Отдельная таблица внешних входов отклонена: провайдер один, а колонка проще в миграции, запросах и откате. При появлении второго провайдера таблица вводится отдельным изменением.

`GoogleSubject` — единственный ключ привязки. Email используется только для первичного поиска аккаунта и никогда не перепривязывает уже связанную идентичность.

### 3. Порядок разрешения Google-идентичности

`GoogleAuthService` (Application) выполняет:

1. Проверяет, что Google вернул непустые `sub` и `email` и `email_verified = true`; иначе отказ.
2. Ищет пользователя по `GoogleSubject`. Если найден — проверяет блокировку и входит, даже если email Google изменился.
3. Ищет пользователя по email без учёта регистра. Если найден:
   - заблокирован — отказ;
   - уже имеет другой `GoogleSubject` — конфликт без изменений;
   - иначе привязывает `sub`, подтверждает email (Google доказал владение) и входит.
4. Если не найден — создаёт подтверждённый аккаунт без пароля с привязкой `sub`.

Уникальные индексы `users.email` и `users.google_subject` — последняя защита от гонок. `DbUpdateException` при сохранении обрабатывается повторным разрешением по subject/email; если состояние несовместимо, возвращается конфликт, а не 500.

### 4. Аккаунт без пароля без nullable-колонки

`password_hash` остаётся `NOT NULL`: при создании через Google записывается хеш случайного 256-битного значения, которое никому не сообщается, а `HasPassword = false` — единственный признак отсутствия пароля. Это сохраняет совместимость с предыдущей версией API при откате: старый код проверяет настоящий хеш, получает отказ и не падает на `NULL`.

`User.CreateWithGoogle(email, googleSubject, placeholderHash, now)` создаёт подтверждённый аккаунт, `HasPassword = false`. `User.SetPassword` выставляет `HasPassword = true`. `LoginAsync` при `HasPassword = false` возвращает то же общее сообщение, что и при неверных данных, не вызывая проверку хеша.

`ProfileService.ChangePasswordAsync` требует текущий пароль только при `HasPassword = true`; для аккаунта без пароля это установка первого пароля. Существующая процедура сброса пароля тоже задаёт пароль и включает обычный вход. Это осознанно расширяет прежнее правило «смена пароля требует текущий» только для аккаунтов, где текущего пароля нет.

### 5. Явная привязка из профиля

`GET /api/auth/google/link` требует авторизации и стартует тот же OAuth с `AuthenticationProperties.Items`:

- `mode = link`;
- `linkUserId` — идентификатор текущего пользователя;
- `returnUrl = /profile`.

`mode` и `linkUserId` защищены correlation-cookie хендлера. На обратном вызове привязка выполняется только если текущая сессия всё ещё принадлежит `linkUserId`; иначе отказ (`session`). Это не даёт привязать Google к чужому аккаунту при смене пользователя в том же браузере.

Важно: `AuthenticationMiddleware` вызывает обработчики callback раньше, чем аутентификацию cookie по умолчанию, поэтому `HttpContext.User` в `OnTicketReceived` для режима привязки не используется. Сессия проверяется явным `HttpContext.AuthenticateAsync(CookieAuthenticationDefaults.AuthenticationScheme)` и сравнением идентификатора из результата с `linkUserId`.

При явной привязке email аккаунта не меняется. Если email Google совпадает с email аккаунта, email аккаунта подтверждается; если отличается — признак подтверждения не меняется. Занятый другим аккаунтом `sub` даёт конфликт.

### 6. Возврат и ошибки — только коды, без текстов исключений

Сервер принимает `redirect` только как локальный путь: начинается с одного `/`, не начинается с `//` или `/\`, не содержит управляющих символов и обратных слэшей. Иначе используется `/`. Итоговый адрес собирается как `App:PublicBaseUrl` + безопасный путь, поэтому в разработке браузер уходит на Vite (`:5173`), а в production — на публичный домен.

Ошибки OAuth не отдаются как ProblemDetails: это браузерный редирект. Сервер перенаправляет на `/login?google=error&reason=<код>` или `/profile?google=error&reason=<код>` с фиксированными кодами: `denied`, `blocked`, `conflict`, `unverified`, `invalid`, `session`, `failed`. Тексты и подробности исключений в URL не попадают; интерфейс переводит коды в русские сообщения. Успешная привязка ведёт на `/profile?google=linked`.

### 7. Публичная доступность провайдера

`GET /api/auth/providers` возвращает только `{ "google": true|false }`. При выключенном провайдере `/api/auth/google/start`, а также `/link` для вошедшего пользователя, отвечают `503` c ProblemDetails и не начинают перенаправление; `/link` без входа сначала получает `401` от политики авторизации. Секреты и client id наружу не отдаются.

Оба стартовых эндпоинта используют существующую политику `Sensitive` (30 запросов в минуту на IP). Обратный вызов защищён `state` и correlation-cookie; отдельный лимит ему не нужен.

### 8. Интерфейс

- `auth` store добавляет `googleEnabled`, `hasPassword`, `isGoogleLinked`; `load()` параллельно запрашивает `/auth/me` и `/auth/providers`, ошибка провайдеров не ломает вход.
- На странице входа кнопка «Войти через Google» — обычная ссылка на `/api/auth/google/start?redirect=...`, а не `fetch`: OAuth требует полноценной навигации. Кнопка показывается только при `googleEnabled`. Ошибки из query `google/reason` показываются через общий маппер кодов.
- В профиле показывается состояние «Google привязан»; если провайдер доступен и привязки нет — ссылка «Привязать Google» на `/api/auth/google/link`. Успех и ошибки читаются из query и очищаются через `router.replace`.
- Если `hasPassword = false`, форма пароля не показывает «Текущий пароль», а называется «Задать пароль». После успешной установки интерфейс перезагружает сведения о пользователе, чтобы форма перешла в обычный режим смены пароля.
- Маппер кодов Google и построение URL выносятся в `frontend/src/api/googleAuth.ts` с юнит-тестами.

### 9. Конфигурация и разработка

Секция `Google` (`ClientId`, `ClientSecret`) читается из настроек и переменных окружения. В production добавляются `Google__ClientId` и `Google__ClientSecret` в `.env` и `docker-compose.prod.yml`.

Redirect URI в Google Cloud Console:

- production: `https://<домен>/api/auth/google/callback`;
- локально: `http://localhost:5000/api/auth/google/callback`, потому что Vite-прокси с `changeOrigin: true` формирует redirect_uri от имени API; после обратного вызова API сам перенаправляет браузер на `http://localhost:5173`.

Это поведение фиксируется в README и `deploy/DEPLOY.md`, чтобы Google не отклонял `redirect_uri_mismatch`.

### 10. Соблюдение platform и отклонения

- Cookie-сессия, единственный источник правил — API, миграции EF Core, ограничение частоты, отсутствие секретов в репозитории сохраняются.
- **Отклонение от `platform`**: OAuth start/callback — GET-навигация браузера, поэтому MVC-antiforgery к ней не применяется; защита от CSRF обеспечивается параметром `state` и защищённой correlation-cookie Google-хендлера. Это эквивалент antiforgery для OAuth-протокола.
- **Отклонение от `platform`**: ошибки обратного вызова OAuth возвращаются редиректом с кодом, а не ProblemDetails, потому что ответ потребляет браузер, а не API-клиент. Ошибки стартовых эндпоинтов остаются ProblemDetails.
- Добавление `Microsoft.AspNetCore.Authentication.Google` не нарушает ограничения первой версии (брокер сообщений/поисковый движок не вводятся).

## Risks / Trade-offs

- **Google недоступен или неверные креды** → стандартный хендлер логирует ошибку, браузер получает `reason=failed`; приложение и парольный вход продолжают работать.
- **Автопривязка по email могла бы быть опасной** → она выполняется только при `email_verified = true`, только к аккаунту без привязки и не для заблокированных; subject всегда приоритетнее email.
- **Гонка двух одновременных входов** → уникальные индексы и повторное разрешение после `DbUpdateException`; при несовместимом состоянии — конфликт.
- **Откат релиза после появления Google-аккаунтов** → схема остаётся совместимой, старая версия отклоняет вход по паролю таких аккаунтов (случайный хеш) и не падает; Google-вход исчезает до повторного релиза. Пользователь может задать пароль через сброс.
- **Пользователь потерял Google-аккаунт** → email аккаунта подтверждён, поэтому доступ восстанавливается существующим сбросом пароля.
- **Утечка client secret** → секрет хранится только в `.env`, не попадает в публичный ответ, логи и репозиторий; при компрометации меняется в Google Cloud Console.
- **Временная cookie `GoogleExternal`** → живёт минуты, `HttpOnly`, не используется ни в одной политике авторизации; после успеха удаляется хендлером/истекает.
- **Смена redirect URI в разработке** → зафиксирована в документации; при переходе на другой порт API или отключении `changeOrigin` её нужно обновить в Google Console.

## Migration Plan

1. Выпустить код и миграцию `add-google-sign-in`: `has_password BOOLEAN NOT NULL DEFAULT true`, `google_subject VARCHAR(255) NULL`, уникальный индекс по `google_subject`. Существующие пользователи получают `has_password = true`.
2. Деплой можно делать без кредов Google: провайдер выключен, кнопка скрыта, парольный вход не меняется.
3. Зарегистрировать OAuth-клиент и redirect URI, добавить `Google__ClientId`/`Google__ClientSecret` в `.env`, пересоздать API (`docker compose -f docker-compose.prod.yml up -d api`).
4. Проверить вход нового Google-пользователя, автоматическую привязку существующего и явную привязку из профиля.
5. Откат приложения не требует отката схемы. Перед релизом всё равно выполняется штатная резервная копия БД; после отката Google-аккаунты остаются в базе и восстанавливаются поздним релизом или сбросом пароля.
