# Design

## Context

См. `proposal.md` — Why. Сейчас:

- `City` хранит `Name` и `IsActive={true}`, в БД включён уникальный индекс по названию.
- `CatalogService.GetCitiesAsync` отдаёт только активные города, `AdService.ResolveCatalogAsync` отвергает неизвестный или неактивный город.
- `CityConfiguration` запрещает удаление города с объявлениями на уровне связи.
- Шаблон административного CRUD уже есть в `CategoryService` и `AdminCategoriesController`.

## Goals / Non-Goals

**Goals:**

- Дать администратору полный цикл управления городами без изменения схемы.
- Сохранить единственным источником правил сервер; интерфейс — надстройка.
- Повторить структуру существующего административного CRUD.

**Non-Goals:**

- Регионы, координаты, массовый импорт.
- Изменение публичных контрактов `/api/catalog/cities`, `/api/ads`.

## Decisions

### 1. Домен `City` — методы вместо прямой записи

`City.Rename`, `Activate`, `Deactivate` и константа `MaxNameLength` (200, совпадает с длиной столбца) сосредоточивают правила в сущности. Сценарий проверяет уникальность имени и существование города, домен — длину.

### 2. `CityService` по образцу `CategoryService`

`GetAdminListAsync`, `CreateAsync`, `RenameAsync`, `ActivateAsync`, `DeactivateAsync`, `DeleteAsync`. Название нормализуется (trim, проверка длины, уникальность без учёта регистра не нужна — индекс по точному имени). Удаление запрещено, если у города есть объявления: возвращается `Conflict` с предложением деактивировать. Так выполняется требование «существующие объявления с городом остаются доступными».

### 3. API под политикой администратора

`AdminCitiesController` (`/api/admin/cities`, политика `Admin`) повторяет форму `AdminCategoriesController`: `GET`, `POST`, `PUT /{id}`, `POST /{id}/activate`, `POST /{id}/deactivate`, `DELETE /{id}`. Модератор получает 403, аноним — 401, потому что политика проверяется на сервере.

### 4. Интерфейс

`AdminCitiesView.vue` на `/admin/cities` использует компоненты дизайн-системы: список городов, поле названия, кнопки сохранения, активации и удаления, сообщения о результате. Пункт «Города» появляется в меню пользователя администратора. Активный город исчезает из выбора при подаче, но остаётся в существующих объявлениях — это обеспечивает публичный эндпоинт.

### 5. Тесты

Интеграционные тесты работают с реальной БД и пропускаются без неё; данные помечаются префиксом и удаляются в `DisposeAsync`. Доменные тесты проверяют методы `City`.

## Risks / Trade-offs

- **Удаление города с объявлениями** → запрещено; администратор деактивирует город. Это сохраняет историю и не рвёт связи.
- **Нет пагинации списка городов** → справочник городов невелик; при росте добавляется отдельной задачей.
- **Переименование не меняет URL** → идентификаторы стабильны, объявления и фильтры ссылаются на `Id`, а не на название.

## Migration Plan

1. Схема не меняется, миграции не создаются.
2. Новые эндпоинты доступны после перезапуска API.
3. Проверка: `dotnet build`, тесты бэкенда, `pnpm --dir frontend test`, `pnpm --dir frontend build`.
4. Откат — предыдущая версия; данные совместимы.
