# Design

## Context

Сейчас `docker-compose.prod.yml` поднимает `postgres`, `api` и `web`, а `web` публикует HTTP-порт на хост. TLS, домен, первичная инициализация и резервное копирование не описаны и не поддержаны кодом. `seed` в `Production` отключён, поэтому справочники и администратор не создаются; письма подтверждения и сброса содержат относительные ссылки, а без SMTP уходят в журнал. См. `proposal.md` — Why.

Ограничения: один VPS, Docker Compose, PostgreSQL в томе, медиа в томе, разработка на Windows (PowerShell 5.1), сервер — Linux. Проверки в CI выполняются на Ubuntu.

## Goals / Non-Goals

**Goals:**

- Развернуть систему с нуля на чистой виртуалке по документу, без устных знаний.
- Выпускать изменения и откатываться по короткой повторяемой процедуре.
- Получать HTTPS автоматически, без ручного продления сертификатов.
- Иметь рабочую почту и абсолютные ссылки в письмах на боевом стенде.
- Иметь ежедневные копии базы и медиа за пределами сервера.

**Non-Goals:**

- Автоматизация выкладки из CI и zero-downtime переключение версий.
- Мониторинг, алертинг и централизованные логи.
- Несколько серверов, балансировка, внешнее объектное хранилище.
- Управление DNS из инструкции: описаны только необходимые записи.

## Decisions

### 1. TLS-терминация — Caddy в составе compose

В `docker-compose.prod.yml` добавляется сервис `caddy` (образ `caddy:2-alpine`) с портами 80 и 443, томами `caddy-data` и `caddy-config`. Конфигурация — `deploy/Caddyfile`:

```
{$DOMAIN} {
    encode gzip
    reverse_proxy web:80 {
        header_up X-Forwarded-For {remote_host}
        header_up X-Forwarded-Proto {scheme}
        header_up X-Forwarded-Host {host}
    }
}
```

Caddy сам получает и продлевает сертификат Let's Encrypt, перенаправляет HTTP на HTTPS, хранит сертификаты в томе (переживают пересборку и откат). `web` перестаёт публиковать порт и получает `expose: ["80"]`.

**Почему не host nginx + certbot:** появляется второй nginx и пакеты на хосте, конфигурация уезжает из репозитория, продление требует cron. **Почему не Cloudflare Tunnel:** меньше открытых портов, но добавляется внешний аккаунт и зависимость; вариант упоминается в `DEPLOY.md` как альтернатива, но не реализуется.

### 2. Проброс схемы и IP через два прокси

Цепочка: клиент → Caddy (HTTPS) → web nginx (HTTP) → api (HTTP). Caddy перезаписывает `X-Forwarded-For` реальным адресом клиента, `deploy/nginx.conf` пробрасывает входящие `X-Forwarded-Proto`/`X-Forwarded-For`/`X-Forwarded-Host`, подставляя `$scheme` при отсутствии заголовка (локальный запуск без Caddy).

В API включается `UseForwardedHeaders` (`XForwardedFor | XForwardedProto`) только вне `Development`, с очисткой `KnownNetworks`/`KnownProxies`: в production порт API не публикуется, доверять можно только внутренней сети compose. Это даёт `Secure`-cookie при HTTPS (`CookieSecurePolicy.SameAsRequest`) и правильный `RemoteIpAddress` для ограничения частоты запросов. В `Development` middleware не включается, чтобы локальный HTTP не ломал вход.

### 3. Абсолютные ссылки в письмах — `IPublicUrlProvider`

Application-слой получает абстракцию `IPublicUrlProvider` с одним свойством `BaseUrl`. Реализация в Infrastructure читает `App:PublicBaseUrl`. `AuthService` строит ссылку как `new Uri(new Uri(baseUrl), "/confirm-email?token=...")`; в `Development` по умолчанию `http://localhost:5173`, в `Production` настройка обязательна и проверяется на старте (fail fast с понятным сообщением). Там же проверяется, что режим почты — `Smtp` и задан `Email:Host`: production не должен молча писать письма в журнал.

**Почему не `LinkGenerator`:** письма формируются в Application-сервисе без HTTP-контекста, а фоновая отправка вообще вне запроса. **Альтернатива** — передавать базовый адрес из контроллера, но тогда логика расходится между точками отправки.

### 4. Инициализация production — две команды вместо `seed`

- `init-data` — идемпотентно создаёт города и категории. Логика выносится из `DemoDataSeeder` в `ReferenceDataSeeder`, который переиспользуют и `seed`, и новая команда.
- `create-admin` — читает `Admin:Email` и `Admin:Password` (переменные `Admin__Email`, `Admin__Password`), проверяет пароль теми же правилами, создаёт пользователя с ролью `Admin` и `IsEmailConfirmed = true`. Если пользователь существует — повышает роль, подтверждает email и обновляет пароль; второго пользователя не создаёт.

Команды запускаются одноразовым контейнером: `docker compose -f docker-compose.prod.yml run --rm api init-data`. `seed` остаётся только для разработки и по-прежнему отказывает в `Production`.

**Почему не включить `seed` в production:** он создаёт три учётные записи с общеизвестным паролем, а удаление демо-аккаунтов после запуска — ручной шаг, который легко забыть.

### 5. Healthcheck и порядок запуска

В образ API добавляется `curl` (рядом с `libgssapi-krb5-2`), healthcheck — `curl -fsS http://localhost:8080/api/health`. У `web` healthcheck через `wget --spider` (есть в alpine-образе nginx). Порядок: `postgres` (healthy) → `api` (healthy) → `web` → `caddy`. Это делает `docker compose up -d` предсказуемым и позволяет скриптам ждать готовности.

### 6. Резервное копирование — скрипты в репозитории

`deploy/backup.sh` (bash, запускается на сервере):

- дамп базы: `docker compose -f docker-compose.prod.yml exec -T postgres pg_dump -U "$POSTGRES_USER" -d "$POSTGRES_DB" | gzip > backups/db-<дата>.sql.gz`;
- медиа: `docker compose ... exec -T api tar -czf - -C /var/www/media . > backups/media-<дата>.tgz`;
- удаление копий старше `BACKUP_KEEP_DAYS` (по умолчанию 14);
- подсказка вынести копии: `rclone sync`/`rsync` на внешний сервер или S3-совместимое хранилище.

`deploy/restore.sh` принимает пути к дампу и архиву, требует явного подтверждения, останавливает `web`/`caddy`, восстанавливает базу через `psql`, распаковывает медиа одноразовым контейнером `api` и запускает сервисы обратно.

Скрипты не хардкодят имя compose-проекта и тома: работают через `docker compose exec/run`, поэтому переживают переименование каталога.

### 7. Структура `deploy/DEPLOY.md`

1. Требования и схема сервисов.
2. **Инструкция 1. Чистая виртуалка:** подготовка сервера (пользователь, SSH, ufw, Docker), DNS, клонирование, `.env`, первый запуск, `init-data`, `create-admin`, почта, бэкапы, проверки (HTTPS, PWA, health).
3. **Инструкция 2. Выпуск изменений:** бэкап → `git pull` → пересборка → ожидание health → проверка → откат.
4. Справочники: переменные окружения, бесплатные SMTP-провайдеры и SPF/DKIM/DMARC, расписание cron, диагностика (логи, `docker compose ps`, проверка сертификата, типовые ошибки).

## Risks / Trade-offs

- **Сертификат не выпустится без DNS и открытого 80 порта** → в инструкции проверка `dig` и `ufw` до первого запуска; при экспериментах — ACME staging, чтобы не упереться в лимиты Let's Encrypt.
- **Два прокси усложняют диагностику** → `X-Forwarded-*` пробрасываются явно, в разделе диагностики — проверка заголовков `curl -I`.
- **Доверие forwarded headers** → middleware включён только в production, API не публикует порт, Caddy перезаписывает `X-Forwarded-For`.
- **Письма попадают в спам** → раздел про SPF, DKIM, DMARC и проверку через mail-tester; отправитель только на собственном домене.
- **Бесплатные тарифы почтовых сервисов меняются** → в документе указаны ориентиры и ссылки, лимиты помечены как проверяемые на момент настройки.
- **Копии лежат рядом с сервером** → скрипт печатает напоминание, в инструкции отдельный шаг выноса и проверка восстановления.
- **Короткий простой при `up -d --build`** → принято для одного сервера; zero-downtime вынесен за рамки.
- **Пароль администратора в переменной окружения** → команда выполняется вручную, переменные не попадают в репозиторий; после создания рекомендуется сменить пароль через интерфейс.

## Migration Plan

Существующего боевого стенда нет; при появлении установки по старой инструкции:

1. Добавить в `.env` `DOMAIN`, `ACME_EMAIL`, `App__PublicBaseUrl`, `Email__*`; убрать `WEB_PORT`.
2. Выполнить `docker compose -f docker-compose.prod.yml up -d --build`; Caddy займёт 80/443, `web` останется внутренним.
3. Выполнить `init-data` и `create-admin`.
4. Проверить HTTPS, регистрацию с письмом и health.

Откат — `git checkout <предыдущая-ревизия>` и повторная сборка; тома `postgres-data`, `media-data`, `caddy-data` сохраняются, миграции аддитивны.
