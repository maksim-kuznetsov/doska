# Design

## Context

См. `proposal.md` — Why. Текущие ограничения:

- `deploy/nginx.conf` не задаёт `client_max_body_size`, поэтому действует значение nginx по умолчанию — 1 МБ.
- `FormOptions.MultipartBodyLengthLimit` в API уже равен 32 МБ, а Kestrel использует значение по умолчанию 30 МБ.
- Интерфейс разрешает 5 фотографий по 5 МБ, то есть до 25 МиБ полезной нагрузки плюс multipart-обвязка.
- Клиент API безусловно вызывает `JSON.parse` для тела ответа, поэтому HTML-ответ прокси с `413` приводит к ошибке разбора.
- Production находится за отдельным внешним прокси, конфигурация которого не входит в репозиторий.

## Goals / Non-Goals

**Goals:**

- Исключить `413` от инфраструктуры для запросов, которые приложение считает допустимыми.
- Показать пользователю понятную причину отказа вместо технической ошибки.
- Защитить конфигурацию репозитория от регрессии в CI.
- Дать оператору точную инструкцию для внешнего прокси.

**Non-Goals:**

- Сжатие или уменьшение фотографий в браузере.
- Изменение лимитов 5 фотографий / 5 МБ.
- Автоматическое управление внешним прокси или CDN/WAF.

## Decisions

### 1. Единый лимит 32 МиБ на всех слоях

`client_max_body_size 32m` задаётся в `location /api/` файла `deploy/nginx.conf`; Kestrel получает такой же `MaxRequestBodySize` через `builder.WebHost.ConfigureKestrel`. Расчёт: 5 × 5 МиБ = 25 МиБ, запас на multipart-заголовки и возможные различия между МиБ и МБ — округление до 32 МиБ. Это больше прикладного максимума, поэтому окончательное решение остаётся за `AdService.ValidatePhotos`.

Альтернативы: точные 26–27 МБ хрупки к изменению числа фото; 64 МБ избыточны и расширяют поверхность для тяжёлых запросов. Лимит только на endpoint через `[RequestSizeLimit]` точнее, но Kestrel-лимит и `FormOptions` уже глобальные, поэтому глобальные 32 МиБ проще и согласованы.

### 2. Явный лимит на внешнем прокси — операционный шаг

Внешний прокси не управляется репозиторием, поэтому в `deploy/DEPLOY.md` добавляется раздел с директивой `client_max_body_size 32m` для nginx, порядком проверки и перезагрузки, а также диагностикой: какой слой вернул `413` (заголовок `Server`, журнал nginx с сообщением `client intended to send too large body`, проверка CDN/WAF). Это позволяет исправить production без изменения кода приложения.

### 3. Устойчивый разбор ошибок в клиенте API

`parseResponse` читает тело как текст, пытается разобрать JSON и при неудаче формирует сообщение по HTTP-статусу. Для `413` используется отдельный текст о слишком больших фотографиях и допустимом размере. `ApiError` и разбор `ProblemDetails` для обычных ошибок API сохраняются.

Альтернатива — ветвление по `Content-Type`: она пропускает ответы с неверным или отсутствующим заголовком. `try/catch` вокруг `JSON.parse` надёжнее и не меняет контракт для JSON-ответов.

### 4. Проверка конфигурации в CI

В job `deployment-scripts` добавляется шаг, который проверяет наличие `client_max_body_size` со значением не меньше 32 МБ и запускает `nginx -t` в контейнере `nginx:1.27-alpine`. При запуске нужно сопоставить имя `api` с локальным адресом (`--add-host api:127.0.0.1`), иначе `nginx -t` попытается разрешить upstream и упадёт в отрыве от compose-сети.

## Risks / Trade-offs

- **Внешний прокси остаётся ручной настройкой** → production не исправится одним деплоем. Смягчение: явный чек-лист в `DEPLOY.md` и проверка загрузки фото 3–5 МБ после настройки.
- **Увеличение допустимого тела запроса** → больше памяти и трафика на границе. Смягчение: лимит фиксирован 32 МБ, endpoint подачи требует авторизации и ограничен по частоте, прикладная проверка отклоняет файлы больше 5 МБ.
- **CI-проверка зависит от формата директивы** → значение вида `33554432` не распознается. Смягчение: сообщение проверки прямо указывает ожидаемую запись `client_max_body_size 32m`, а `nginx -t` ловит синтаксические ошибки.
- **Разные причины `413`** → ошибка может приходить от CDN/WAF, а не от nginx. Смягчение: диагностика по заголовкам и журналам, без изменения кода.

## Migration Plan

1. Выпустить изменения репозитория: пересобрать `web` и `api`; миграции не требуются.
2. На сервере внешнего прокси задать `client_max_body_size 32m`, проверить `nginx -t` и перезагрузить прокси.
3. Проверить подачу объявления с фотографией 3,4 МБ (ожидается `201`) и с фотографией около 5 МБ.
4. Откат: вернуть предыдущие образы и конфигурацию прокси; данные и схема не затрагиваются.

## Open Questions

- Точный путь к конфигурации внешнего прокси и наличие перед ним CDN/WAF определяются оператором на сервере; на подход и состав задач это не влияет.
