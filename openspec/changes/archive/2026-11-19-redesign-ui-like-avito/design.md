# Design

## Context

См. `proposal.md` — «Why». Ограничения и текущее состояние:

- Интерфейс — SPA на Vue 3 + TypeScript + Vite; всё оформление сосредоточено в дизайн-системе: `frontend/src/assets/css/tokens.css` (единственный источник визуальных значений), `base.css`, `components.css`, `layout.css`. Представления не вводят собственных классов оформления.
- Уже есть заготовки под Avito: палитра (`#00AAFF`, `#FF6163`, `#97CF26`, `#A169F7`) и стек шрифтов с «Avito Sans» в `tokens.css`.
- Данные интерфейса приходят только из Web API (`/api`, относительные адреса через прокси Vite); прямой доступ к БД запрещён. Каталог разделов и городов уже доступен (`api.catalog.sections()`, `api.catalog.cities()`).
- Тесты интерфейса — Vitest, рядом с кодом в `frontend/src/**/__tests__/*.spec.ts`; есть e2e (Playwright).
- Текущее требование design-system прямо запрещает постоянную полосу категорий в шапке — это изменение его снимает (см. дельту спецификации).

## Goals / Non-Goals

**Goals:**

- Привести визуальный язык и раскладку всего интерфейса к облику avito.ru, оставаясь внутри дизайн-системы (токены + переиспользуемые компоненты).
- Добавить структурные блоки Avito: постоянную полосу категорий и выбор города в шапке, блок разделов плитками и промо-баннер на главной.
- Сохранить единый источник оформления, доступность и адаптивность, не меняя бизнес-логику и API.

**Non-Goals:**

- Изменение бэкенда, схемы данных, API и бизнес-правил.
- Копирование фирменных ресурсов Avito (логотип, лицензионные шрифтовые файлы).
- Тёмная тема, новые языки интерфейса, управление контентом промо из админки.

## Decisions

### D1. Остаёмся на текущей CSS-архитектуре, без UI-фреймворка

Расширяем существующие слои `tokens.css` → `base.css` → `components.css`/`layout.css` и добавляем компоненты Vue. Альтернатива — подключить готовый UI-набор (Vuetify и т.п.) — отклонена: ломает требование «единый источник оформления», тянет крупную зависимость и конфликтует с площадкой из `platform/spec.md`.

### D2. Расширение токенов, а не переопределение значений в компонентах

Добавляем в `tokens.css` токены под нужды Avito: соотношение сторон изображения карточки, ширина контейнера/сетки, отступы сетки, высоты шапки и полосы категорий, состояния наведения карточки. Значения цветов палитры не меняются (они уже соответствуют спецификации). Любое значение остаётся в единственном источнике.

### D3. Новые переиспользуемые компоненты вместо кода в представлениях

- `CategoryStrip.vue` — постоянная горизонтальная полоса разделов под шапкой (настольная ширина), с горизонтальной прокруткой без переноса.
- `CitySelect.vue` — выбор города в шапке; значение уходит в фильтр ленты (`cityId`).
- `CategoryTiles.vue` — блок разделов/подразделов плитками на главной.
- `PromoBanner.vue` — промо-баннер с заголовком и действием «Подать объявление».

Это сохраняет требование «представления собираются из компонентов системы». Альтернатива — верстать блоки прямо в `HomeView`/`SiteHeader` — отклонена как нарушение единого источника.

### D4. Шапка: поиск по центру, полоса категорий на настольной ширине, бургер на мобильной

`SiteHeader` перестраивается: основная строка (бренд, город, крупный поиск, «Подать объявление», меню пользователя) плюс `CategoryStrip` под ней. На мобильной ширине полоса скрывается, категории открываются существующим `CategoryMenu` (бургер). Источник данных — тот же `api.catalog`.

### D5. Город в шапке связан с параметрами ленты, а не с отдельным хранилищем

Выбранный город отображается в шапке и записывается в query-параметр ленты (`cityId`), который уже поддерживает существующий `search.ts`. Альтернатива — отдельный Pinia-стор — отклонена: дублирует состояние фильтров и создаёт рассинхронизацию.

### D6. Карточка и строка списка — единые пропорции через `aspect-ratio`

`AdCard`/`AdRow` используют фиксированное соотношение сторон изображения и плейсхолдер того же размера, цену как акцент. Сетка ленты — `grid` с адаптивным числом колонок. Это делает поведение (сценарии дельты) проверяемым и стабильным.

### D7. Обновление страницы-гайда и тестов вместе с кодом

`DesignSystemGuide.vue` дополняется примерами новых компонентов и токенов (доступна только в `Development`). Существующие `*.spec.ts`, привязанные к разметке, обновляются; на новые компоненты добавляются тесты в `__tests__`.

## Risks / Trade-offs

- [Существующие тесты завязаны на текущую разметку/классы] → обновлять тесты в той же задаче, что и компонент; прогон `pnpm test` после каждого блока.
- [Крупный объём CSS-изменений может незаметно задеть нецелевые страницы] → менять оформление преимущественно через токены и общие классы, проверять гайд и ключевые страницы вручную (`docker compose`).
- [Широкие таблицы/сетки могут вызвать горизонтальную прокрутку на мобильной ширине] → явные сценарии адаптивности в дельте и проверка на мобильной ширине.
- [Соблюдение предупреждения о длине описаний требований] → описания требований короткие, детали в сценариях.

## Migration Plan

Изменение чисто внешнее (frontend), миграции данных и API нет.

1. Расширить токены и общие стили.
2. Добавить новые компоненты и перестроить шапку/главную.
3. Обновить остальные представления под новые токены и компоненты.
4. Обновить страницу-гайд и тесты.
5. Проверка: `pnpm test` в `frontend/`, затем ручной просмотр ключевых страниц через `docker compose`.

Откат — обычный откат релиза интерфейса (предыдущая версия статики по хешу из `static-assets/spec.md`); данные не затрагиваются.

## Open Questions

Нет: все развилки, влияющие на спецификацию, подход и разбиение задач, решены выше (D3–D6).
