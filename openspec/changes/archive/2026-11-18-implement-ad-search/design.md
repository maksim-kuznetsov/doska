# Design

## Context

See `proposal.md` — Why. Текущее состояние:

- `Ad` хранит статус, цену, город, подраздел, `PublishedAt`; объявления создаются и модерируются, статус `Active` — единственный публичный.
- `CatalogService` уже отдаёт города и подразделы; `AppDbContext` работает через EF Core и PostgreSQL.
- Схема БД покрывает поиск: `ads (status, published_at)`, `ads (category_id, status)`, `ads (city_id)`, `ads (author_id, created_at)`. Миграции не нужны.

## Goals / Non-Goals

**Goals:**

- Реализовать публичную выдачу ровно по требованиям `ad-search`: видимость, текст, фильтры, сортировка, пагинация.
- Сохранить состояние фильтров в URL, чтобы страница переживала перезагрузку и ссылка была воспроизводимой.

**Non-Goals:**

- Полнотекстовый движок, морфология, подсказки, релевантность.
- Фотографии в карточках, страница объявления, отклики.
- Кэширование выдачи.

## Decisions

### 1. Поиск средствами PostgreSQL без внешнего движка

Условие поиска — `lower(title) LIKE '%текст%' OR lower(description) LIKE '%текст%'`, выражаемое через EF `ToLower().Contains(...)`. Это точное вхождение без учёта регистра и без трактовки `%`/`_` как шаблонов, в отличие от `ILIKE`. Альтернативы: `pg_trgm`/GIN и `tsvector` — быстрее на больших объёмах, но требуют расширения и отдельной настройки; по `platform` первая версия обходится средствами PostgreSQL, поэтому оставляем простой вариант и индексы, уже созданные для `status`/`published_at`.

### 2. Фильтр категории принимает и раздел, и подраздел

Условие: `ad.CategoryId == categoryId || ad.Category.ParentId == categoryId` вместе с `ad.Category.IsActive`. Если выбран подраздел, срабатывает первое условие; если раздел верхнего уровня — второе, и в выдачу попадают объявления всех его активных подразделов. Объявления деактивированного подраздела остаются доступными в общей ленте и поиске, как требует `categories`. Альтернатива — заранее собирать список id подразделов отдельным запросом: лишний round-trip и риск разойтись с деревом; одно условие проще и остаётся корректным при изменении справочника.

### 3. Публичный эндпоинт `GET /api/ads`

`AdsController` уже имеет `[Authorize]`; на действии поиска ставится `[AllowAnonymous]`, что перекрывает контроллерную авторизацию. Отдельный контроллер с тем же префиксом не нужен. Существующие `POST /api/ads` и `GET /api/ads/mine` остаются защищёнными.

### 4. Контракт пагинации и значения по умолчанию

Параметры: `page` (с 1), `pageSize` (1–50, по умолчанию 12). Некорректные значения нормализуются (`page = max(1, page)`, `pageSize` зажимается в диапазон), а `minPrice > maxPrice` даёт 400 с `ProblemDetails`. Неизвестная сортировка трактуется как `newest`, чтобы ссылка не ломалась. Ответ: `{ items, totalCount, page, pageSize }`, где `totalCount` считается до пагинации.

### 5. Сортировка

`newest` — `PublishedAt desc`, затем `CreatedAt desc` для устойчивости; `price_asc` — `Price asc, PublishedAt desc`; `price_desc` — `Price desc, PublishedAt desc`. Дополнительный ключ убирает «прыжки» объявлений с одинаковой ценой между страницами.

### 6. Видимость и заблокированные авторы

Базовое условие выдачи: `Status == Active` и `Author.BlockedAt == null`. Второе условие выполняет требование `user-accounts` о скрытии объявлений заблокированного автора, не добавляя отдельного сценария.

### 7. Состояние фильтров на клиенте — query-параметры маршрута

Главная страница читает фильтры из `route.query`, а изменения пишет обратно через `router.push`. Пагинация меняет только `page`, поэтому фильтры сохраняются автоматически. Помощники `readFilters`, `toRouteQuery`, `toSearchParams` вынесены в `frontend/src/api/search.ts`, чтобы правила формирования запроса тестировались без монтирования страницы.

## Risks / Trade-offs

- **Поиск вхождением без индекса по тексту** → на объёмах первой версии приемлемо; при росте оформляется отдельное изменение с `pg_trgm`/GIN.
- **Фильтр по разделу зависит от `ParentId`** → объявления создаются только в подразделах (проверка в `AdService`), поэтому у активного объявления `ParentId` заполнен.
- **Некорректная страница за пределами выдачи** → возвращается пустой `items` с корректным `totalCount`; клиент показывает «ничего не найдено».
- **`ToLower().Contains()` может не использовать индекс** → принято осознанно; альтернатива с `ILIKE` требует экранирования шаблонов.

## Migration Plan

1. Схема не меняется, миграции не создаются.
2. Проверка: `dotnet test backend/Doska.sln` (или прямой запуск тестового exe), `pnpm --dir frontend test`, `pnpm --dir frontend build`.
3. Откат — предыдущая версия приложения; данные совместимы.
