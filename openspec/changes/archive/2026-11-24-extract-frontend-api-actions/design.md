# Design

## Context

См. `proposal.md` — Why. Клиентские ошибки приходят как `ApiError` (`frontend/src/api/client.ts:170`) с готовым `message`; транспорт (`request`/`requestForm`/`fetchCsrfToken`) уже централизован в `client.ts`. Дублируется не транспорт, а реакция интерфейса на ошибку и обёртка действия над API. В admin-представлениях обёртка `run` дополнительно перечитывает данные через `load()` после успеха.

## Goals / Non-Goals

**Goals:**

- Единый источник преобразования ошибки в текст.
- Единая обёртка «очистить сообщения → выполнить действие → уведомление → при необходимости перечитать → показать ошибку».

**Non-Goals:**

- Не менять контракт `client.ts` и формат `ProblemDetails`.
- Не унифицировать тексты fallback — они остаются на месте вызова.

## Decisions

- **Где разместить код.** Чистая функция `messageOf(cause, fallback)` — в `frontend/src/api/errors.ts`; обёртка с состоянием — в `frontend/src/composables/useApiAction.ts`. Альтернатива «всё в `client.ts`» отклонена: смешала бы транспорт и UI-состояние Vue.
- **Сигнатура composable.** `useApiAction(reload?: () => Promise<void>)` возвращает `{ error, notice, run }`; `run(action, success, fallback)` очищает сообщения, выполняет действие, ставит уведомление, при необходимости вызывает `reload()` и при ошибке пишет `messageOf(cause, fallback)`. Альтернатива с обязательным `reload` отклонена: не все вызовы перечитывают данные.
- **`messageOf` экспортируется отдельно**, потому что `load()` в представлениях использует его напрямую.
- **Fallback-тексты** передаются на месте вызова и сохраняются дословно.

## Risks / Trade-offs

- Разные представления задают свой fallback для «действия» → параметр сохраняет тексты; сверить все 21 место перед удалением копий.
- `run` в admin-views перечитывает данные, в остальных — нет → `reload` опционален.
- Ошибки, не являющиеся `ApiError`, теряют детали → поведение не меняется, fallback сохраняется.
