# Design

## Context

См. `proposal.md` — мотивацию. Текущее состояние, задающее подход:

- Сущность `User` (`Doska.Domain/Entities/User.cs`) инкапсулирована: состояние меняется только доменными методами, отметки времени проставляет домен (требования `platform`).
- Сведения о вошедшем пользователе формирует `AuthenticatedUser.From(User)` (`Doska.Application/Auth/AuthService.cs`) и отдаёт `GET /api/auth/me` (`UserResponse`). Интерфейс уже загружает этот ответ в `stores/auth.ts`.
- Контакты объявления — одно свободное поле `Ad.Contacts` до 500 символов (`AdService.MaxContactsLength`).
- Изменяющие запросы требуют antiforgery-токен; чувствительные операции ограничиваются по частоте (`RateLimitPolicies.Sensitive`).
- Административное управление (`UserService`, `UsersController`) трогать не требуется.

## Goals / Non-Goals

**Goals:**

- Хранить у пользователя отображаемое имя и контакты одной строкой и менять их доменным методом.
- Дать странице профиля чтение/запись профиля и смену пароля.
- Отдавать профиль в `/api/auth/me`, чтобы форма объявления предзаполняла контакты без отдельного запроса.

**Non-Goals:**

- Структурированные контакты, аватары, прочие поля профиля (см. «Вне рамок» в proposal).
- Инвалидация других активных сессий при смене пароля.
- Отдельный `GET` профиля: чтение закрывает расширенный `/api/auth/me`.

## Decisions

**1. Модель: два необязательных строковых столбца у `User`.**

`DisplayName` (до 100 символов) и `Contacts` (до 500, как `Ad.Contacts`), оба `string?`. Домен получает метод `UpdateProfile(string? displayName, string? contacts, DateTimeOffset now)`, который обрезает пробелы, пустые строки превращает в `null` и вызывает `MarkUpdated`. Отдельная сущность «профиль» не нужна: поля принадлежат пользователю один-к-одному, а `User` уже несёт остальные его атрибуты.

**2. Эндпоинты: расширить `/api/auth/me`, запись — в новом `AccountController` (`api/account`).**

- `GET /api/auth/me` — `UserResponse` дополняется `DisplayName` и `Contacts` (нужно для подстановки).
- `PUT /api/account/profile` — сохраняет отображаемое имя и контакты, возвращает обновлённый `UserResponse`.
- `POST /api/account/password` — смена пароля, тело `{ currentPassword, newPassword }`.

Альтернатива — складывать всё в `AuthController`. Отклонено: вход/регистрация и ведение профиля — разные зоны ответственности, а `UsersController` занят модерацией и доступен только модератору/администратору.

**3. Сервис: `ProfileService` в `Doska.Application/Accounts`.**

`UpdateAsync(userId, displayName, contacts)` и `ChangePasswordAsync(userId, currentPassword, newPassword)`. Валидация: контакты ≤ 500, имя ≤ 100 — иначе `ServiceException(Validation, ...)`. Смена пароля проверяет текущий через `IPasswordHasher` и переиспользует `AuthService.ValidatePassword` для нового; при неверном текущем — `Unauthorized`. `ProfileService` группирует обе операции, чтобы контроллер зависел от одного сервиса; `AuthService` не разрастается.

**4. Смена пароля защищена как чувствительная операция.**

Эндпоинт помечается `[Authorize]` и `[EnableRateLimiting(RateLimitPolicies.Sensitive)]`; antiforgery уже обеспечивается общей инфраструктурой.

**5. Интерфейс: страница `ProfileView` и предзаполнение в `AdFormView`.**

- Новый маршрут `/profile` (`requiresAuth`), пункт «Профиль» в `UserMenu.vue`.
- Две формы: профиль (имя, контакты) и смена пароля (текущий, новый). Для нового пароля переиспользуется компонент `PasswordHints.vue`; серверная проверка остаётся источником правил.
- Клиент API: `api.account.updateProfile(...)`, `api.account.changePassword(...)`; тип `CurrentUser` получает `displayName`/`contacts`.
- `stores/auth.ts` после сохранения профиля обновляет `user` из ответа, чтобы данные были актуальны сразу.
- `AdFormView.vue` при монтировании подставляет в поле «Контакты» отображаемое имя и контакты профиля, соединённые одним пробелом (пустые части пропускаются), если поле пустое. Подстановка односторонняя: правки в форме не пишутся в профиль.

**6. Миграция EF Core `AddUserProfile`.**

Добавляет в `users` необязательные `display_name varchar(100)` и `contacts varchar(500)`. Конфигурация — в `UserConfiguration`. Столбцы nullable, поэтому миграция безопасна на существующих данных.

## Risks / Trade-offs

- [Предзаполнение затирает введённое] → подстановка выполняется один раз при открытии пустой формы нового объявления и не перезаписывает уже введённый текст; поле остаётся редактируемым.
- [Устаревшие данные профиля в хранилище] → после сохранения профиля `stores/auth.ts` обновляет пользователя из ответа сервера.
- [Смена пароля не разлогинивает другие сессии] → принято осознанно (вне рамок); при необходимости — отдельное изменение.
- [Расхождение правил длины контактов] → предел 500 совпадает с `AdService.MaxContactsLength`; оба значения проверяются на сервере.

## Migration Plan

1. Миграция `AddUserProfile` применяется при развёртывании до обработки запросов (существующий механизм `platform`).
2. Откат: столбцы необязательные и не используются старым кодом, поэтому откат кода не требует удаления данных; при необходимости — обратная миграция.
